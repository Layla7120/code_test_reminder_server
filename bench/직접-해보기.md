# 직접 해보기 — 랭킹 Redis on/off 체감하기

읽는 것과 8초를 실제로 기다려보는 건 완전히 다릅니다.
터미널 2개를 띄워놓고 순서대로 따라가시면 됩니다.

## 용어

**조건(arm)** = A/B 테스트에서 비교하는 각각의 설정. 여기서는 딱 하나만 다릅니다.

| 조건 | 설정 | 랭킹을 어디서 읽나 |
|---|---|---|
| **Redis 조건** | `RANKING_REDIS_ENABLED=true` | Redis ZSET (`ZREVRANGE`) |
| **DB 조건** | `RANKING_REDIS_ENABLED=false` | MySQL `DENSE_RANK()` — 전체 유저 정렬 |

DB 조건은 벤치마크용으로 새로 만든 게 아니라, **운영에 이미 있는 Redis 장애 폴백 경로**입니다.
그래서 이 실험은 "Redis가 죽으면 어떻게 되나"를 그대로 재현하는 것이기도 합니다.

## 1. DB 조건으로 켜서 손으로 눌러보기

### 터미널 A — 서버 켜기

```bash
RANKING_REDIS_ENABLED=false RANKING_SYNC_CRON="0 0 0 1 1 ?" \
  java -jar server/build/libs/server-0.0.1-SNAPSHOT.jar
```

`Started ServerApplication` 이 뜰 때까지 기다립니다.

> `RANKING_SYNC_CRON="0 0 0 1 1 ?"` 은 자가치유 스케줄러를 1월 1일로 밀어
> 측정 중에 끼어들지 못하게 하는 겁니다. 10만 ZSET을 다시 읽는 배치가
> 측정 도중 돌면 숫자가 튑니다.

### 터미널 B — 호출

```bash
curl -s -o /dev/null -w "%{time_total}초\n" http://localhost:8080/rank
```

**여기서 한 번 세어보세요.** 유저 10만 기준으로 약 **8초**입니다.
동시 요청이 하나도 없는데도 이렇습니다.

개인 순위도:

```bash
curl -s -o /dev/null -w "%{time_total}초\n" "http://localhost:8080/rank/users?userId=7"
```

약 1.2초.

## 2. Redis 조건으로 바꿔보기

### 터미널 A — `Ctrl+C` 로 끄고 다시 켜기

```bash
RANKING_REDIS_ENABLED=true RANKING_SYNC_CRON="0 0 0 1 1 ?" \
  java -jar server/build/libs/server-0.0.1-SNAPSHOT.jar
```

### 터미널 B — 같은 명령

```bash
curl -s -o /dev/null -w "%{time_total}초\n" http://localhost:8080/rank
```

**약 0.004초.** 방금 8초 기다린 것과 같은 요청, 같은 데이터입니다.

> ### 함정 하나 — Redis가 비어 있으면 조용히 DB로 갑니다
>
> Redis 조건인데도 8초가 나온다면 Redis가 비어 있는 겁니다.
> `getTop30()` 은 Redis가 비면 **에러 없이** DB 폴백을 탑니다.
> 확인:
> ```bash
> docker exec -i reminder-redis redis-cli ZCARD rank:commit:$(TZ=Asia/Seoul date +%Y%m)
> ```
> 유저 수와 같아야 합니다. 다르면 아래 4번(워밍업)을 하세요.

## 3. 30명이 동시에 들어오면 (k6)

여기가 제일 볼만합니다.

### 터미널 A — DB 조건으로 켜기

```bash
RANKING_REDIS_ENABLED=false RANKING_SYNC_CRON="0 0 0 1 1 ?" \
  java -jar server/build/libs/server-0.0.1-SNAPSHOT.jar
```

### 터미널 B

```bash
k6 run -e USERS=100000 bench/rank_ab.js
```

**화면을 보고 계세요.** 60초 동안 처리한 요청이 200건대에서 멈추고,
`http_req_failed` 가 80%대까지 올라갑니다.

터미널 A의 서버 로그에도 이게 쏟아집니다:

```
HikariPool-1 - Connection is not available, request timed out after 3005ms
             (total=20, active=20, idle=0, waiting=9)
```

쿼리 하나가 수 초씩 커넥션을 붙잡으니 20개짜리 풀이 즉시 포화되고,
뒤에 온 요청은 **쿼리를 시작해보지도 못하고** 3초 뒤 5xx로 떨어집니다.

### 이제 Redis 조건으로 같은 걸

터미널 A에서 `Ctrl+C` → `RANKING_REDIS_ENABLED=true` 로 재시작 → 터미널 B에서 같은 k6 명령.

**55만 건 처리, 실패 0%.**

## 4. 규모를 바꿔서 기울기 느끼기

지금까지는 10만 명이었습니다. 1만 명으로 줄여보면 기울기가 보입니다.

**0번의 시드 + 워밍업을 `@target_users = 10000` 으로 다시 하면 됩니다.**
(시드 스크립트가 기존 데이터를 `TRUNCATE` 로 지우고 새로 만듭니다)

그다음 1~3번을 그대로 반복하세요.

### 비교해볼 값 (제가 잰 결과)

동시 요청 없이 `GET /rank` 한 번:

| 유저 수 | DB 조건 | Redis 조건 |
|---|---|---|
| 1만 | 1.5초 | 0.003초 |
| 5만 | 3.7초 | 0.004초 |
| 10만 | **8.0초** | **0.004초** |

**Redis 쪽은 평평하고 DB 쪽만 올라갑니다.** 이게 "기울기가 다르다"의 실체입니다.

## 알아두면 좋은 함정 두 개

### 타임존
MySQL 컨테이너는 UTC, 앱은 Asia/Seoul입니다.
KST 기준 매월 1일 0~9시 사이에는 두 시계의 "이번 달"이 다릅니다.
시드 스크립트에 `SET time_zone = '+09:00';` 이 들어 있는 이유입니다.
없으면 시드한 커밋이 전부 "지난달"로 분류되어 **랭킹이 조용히 0건**이 됩니다.

### 시드 지우기
200만 행 규모에서 `DELETE` 는 10분을 넘깁니다. 스크립트는 `TRUNCATE` 를 씁니다.
