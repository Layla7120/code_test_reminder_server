# 코테독촉기 — Flask에서 Kotlin/Spring Boot로

알고리즘 문제 풀이 독려 서비스. Flask로 만들어 운영하다 Kotlin + Spring Boot로 옮겼다.

이 문서는 **무엇을 왜 바꿨는지, 그리고 그게 맞다는 걸 어떻게 확인했는지**의 기록이다.
각 항목에는 그 주장을 증명하는 테스트가 붙어 있다. 테스트가 없는 항목은 없다고 적었다.

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
cd server && ./gradlew test     # 26개, Testcontainers로 실제 MySQL·Redis 기동
```

## 시점 구분 — 언제 무엇을 했나

세 시기를 섞지 않는 게 이 문서의 첫 번째 원칙이다.

| 시기 | 한 일 |
|---|---|
| **① Flask 운영 중** | 부하 테스트로 쿼리 병목 발견 → 인덱스·시점 계산 교정 (커밋 `0bd802f`, 2026-03) |
| **② Kotlin 전환** | 엔티티·리포지토리 재설계, Redis 랭킹 도입 |
| **③ 테스트 도입 이후** | 테스트를 붙이는 과정에서 **전환 때 놓친 결함 6개**를 새로 발견하고 수정 |

③이 이 프로젝트에서 가장 배운 게 많은 구간이었다.
전환 당시엔 "고쳤다"고 생각했지만 증명이 없었고, 실제로 증명을 붙여보니 틀린 게 나왔다.

## ① Flask 단계에서 고친 것

**이건 마이그레이션 성과가 아니다.** Flask로 운영하던 중에 고쳤다.

### 인덱스를 못 타던 쿼리

```sql
-- 문제: 컬럼을 함수로 감싸면 B-Tree 인덱스 탐색이 불가능해진다
WHERE extract(year FROM commit_date) = ... AND extract(month FROM commit_date) = ...
```

`commit_date`에 인덱스가 있어도 무용지물이었다. 5만 건 Full Scan.

**해결**: 서비스 레이어에서 범위를 계산해 넘기고, 쿼리는 `commit_date >= :start AND < :end` 형태로 바꿨다.
`commit_date` 인덱스도 이때 추가했다. (1월에 `previous_year`가 틀리던 버그도 같이 잡음)

### 랭킹 응답 캐싱

동일 결과를 반환하는 `/rank`에 60초 캐시(Flask-Caching)를 적용했다.

### 결과

k6 부하 테스트(VU 50, 50초): **p95 4,234ms → 86ms**

> 이 수치는 **Flask 단계의 성과**다. Kotlin 전환과는 무관하다.
> 이전 버전 문서는 이 숫자를 마이그레이션 서두에 배치해 전환 성과처럼 읽히게 했다 — 잘못이었다.

## ② Kotlin 전환에서 설계로 바꾼 것

### 스택 비교

| 항목 | Flask | Kotlin/Spring Boot |
|---|---|---|
| 언어/프레임워크 | Python 3.11 + Flask 3.1 | Kotlin + Spring Boot 4.0 |
| ORM | SQLAlchemy 2.0 | Spring Data JPA (Hibernate) |
| DB | MySQL | MySQL (동일) |
| 캐싱 | Flask-Caching (SimpleCache, 프로세스 로컬) | Redis (공유) |
| 커넥션 풀 | SQLAlchemy Pool | HikariCP |
| 스키마 관리 | Alembic | **없음 — `infra/init.sql` 수동 관리** |
| 테스트 | 없음 | Testcontainers (실제 MySQL·Redis) |

> **스키마 마이그레이션 도구를 쓰지 않는다.** 이전 문서는 "Flyway"라고 적었으나 도입하지 않았다.
> 판단 근거는 아래 "알고 있으나 하지 않은 것" 참조.

### 결함 1. Participate 복합키 → 대리키 + UNIQUE

```python
# Flask: 자연 복합키
group_id = db.Column(db.Integer, primary_key=True)
user_id  = db.Column(db.Integer, primary_key=True)
```

JPA에서 복합키는 `@EmbeddedId`/`@IdClass`가 필요하고 `equals`/`hashCode` 계약을 지켜야
1차 캐시가 정상 동작한다. 대리키 `participate_id` + `uk_participate_group_user` UNIQUE로 분리했다.

**비즈니스 식별은 UNIQUE 제약이, JPA 관리는 숫자 PK가** 담당한다.

### 결함 2. member_counter Lost Update — 3단계 시행착오

```python
# Flask: 읽고-고치고-쓰기. 정원 확인은 별도 문장에서.
group.member_counter += 1
db.session.commit()
```

동시에 두 명이 마지막 자리에 들어오면 둘 다 통과한다.

| 시도 | 결과 |
|---|---|
| 1차: 컬럼 제거, `participations.size` 사용 | LAZY 컬렉션 전체 로딩 → **OOM 위험** |
| 2차: `COUNT` 조회 후 INSERT | 두 요청이 동시에 같은 값을 읽음 → **TOCTOU** |
| 최종: 컬럼 유지 + DB 원자적 조건부 UPDATE | 해결 |

```kotlin
UPDATE Group g SET g.memberCounter = g.memberCounter + 1
WHERE g.id = :groupId AND g.memberCounter < g.memberMaxCount
// 반환값 1 = 성공, 0 = 정원 초과
```

조건 확인과 증가가 **단일 원자 연산**이다. 엔티티를 메모리에 올리지도 않는다.

> **증명 테스트**: `GroupJoinConcurrencyTest`
> - 정원 1자리에 20명 동시 요청 → 정확히 1명 성공
> - 대조군: 자리가 충분하면 20명 전원 성공 (앞 테스트가 고장난 게 아님을 보임)
>
> **빨간불 확인함**: 구현을 TOCTOU 버전으로 일시 교체하니 `expected: 1 but was: 7`.
> 20명 중 7명이 통과했다. 실행할 때마다 숫자가 달라진다 —
> 스레드 스케줄링에 따라 몇 명이 낡은 값을 보는지가 바뀌기 때문이다.

### 결함 3. 커밋 수집 중복 요청 → Redis 분산 락

Flask는 DB의 `on_duplicate_key_update`에만 의존했다. 동시에 3번 호출되면
GitHub API도 3번 호출되고 DB 락 경합이 생긴다.

```kotlin
val acquired = redisTemplate.opsForValue()
    .setIfAbsent("commit:fetch:lock:$userId", "1", Duration.ofSeconds(30))
if (acquired != true) throw CommitFetchAlreadyInProgressException()
```

> 이 락에는 **전환 당시 놓친 결함**이 있었다. 아래 결함 9 참조.

### 결함 4. 단건 Upsert 루프 → 배치

100건이면 네트워크 왕복 100번이었다. `JdbcTemplate.batchUpdate(chunk=100)`으로 1번.

sha 기준 오름차순 정렬 후 삽입한다 — InnoDB Next-Key Lock이 인덱스 순서로 잡히므로,
여러 스레드가 **같은 순서로** 락을 요청하면 사이클이 생기지 않아 데드락이 방지된다.

### 결함 5. Native Query 남용 → 필요한 곳만

윈도우 함수가 필요한 랭킹 쿼리만 Native Query로 두고 나머지는 JPQL + 인터페이스 Projection으로 바꿨다.
`List<Commit>` 대신 필요한 컬럼만 스칼라로 받아 영속성 컨텍스트 오염을 피한다.

### 결함 6. 테스트 불가능한 시각 처리 → Clock 주입

Flask는 모듈 로드 시점의 `TODAY` 상수를 썼다. 프로세스가 살아 있으면 날짜가 안 바뀌고,
특정 시점을 재현할 수도 없었다.

```kotlin
@Bean fun clock(): Clock = Clock.system(ZoneId.of("Asia/Seoul"))
```

> **증명 테스트**: `ClockInjectionTest`
> `Clock.fixed(2026-08-01)`로 갈아끼우고 월 경계 앞뒤(7/31 23:59:59, 8/1 00:00:00)에
> 커밋을 심어, 이번달/저번달이 고정된 시계 기준으로 정확히 나뉘는지 확인.

## ③ 테스트를 붙이며 새로 발견한 것

여기부터가 "전환 때 고쳤다고 생각했지만 실제로는 틀렸던" 것들이다.

### 결함 7. ★ 랭킹 점수 이중 계상 — 안전장치 두 개가 서로를 무력화

**이 프로젝트에서 가장 배운 게 많은 결함이다.**

커밋 수집은 이 순서로 동작했다.

1. GitHub에서 커밋 5개를 받는다
2. DB에 저장한다 — `ON DUPLICATE KEY UPDATE`라 이미 있는 건 건너뛴다
3. 랭킹 점수를 올린다 — **그런데 "5점"을 그대로 더했다**

2번에서 실제로 0건이 들어가도 3번은 5점을 더한다.
같은 요청을 세 번 보내면 DB는 커밋 5개 그대로인데 랭킹은 15점이 된다.

**그럼 매시간 도는 자가 치유 스케줄러가 고쳐주지 않나?** 안 고쳐준다.

스케줄러는 DB를 세어 Redis를 보정하는데, **점수를 올리기만 하고 내리지는 않는다.**
그렇게 만든 이유가 있다 — 스케줄러가 DB를 읽는 동안 사용자가 새 커밋을 올리면,
스케줄러가 방금 오른 점수를 낡은 스냅샷으로 덮어써서 증분을 날려버린다.
그걸 막으려고 "현재값보다 클 때만 갱신"(ZADD GT) 규칙을 넣었다.

```
랭킹: 15점 / DB 실제: 5개
스케줄러: "5는 15보다 작다 → 갱신 안 함"
→ 15점 그대로. 영구히.
```

**Lost Update를 막으려고 넣은 장치가, 잘못된 값의 하향 보정까지 막았다.**

**왜 못 찾았나** — 부하 테스트용 `MockGithubClient`가 호출할 때마다 새 UUID를 sha로 만들었다.
중복이 구조적으로 발생할 수 없으니 이 버그가 나타날 방법이 없었다.

**해결** — GT 규칙은 그대로 두고, **증분을 정확하게** 만들었다.
삽입 전에 기존 sha를 조회해 실제 신규 커밋만 랭킹에 반영한다.
버킷도 서버의 "지금"이 아니라 각 커밋의 실제 `commitDate` 기준으로 나눠 발행한다
(월초에 지난달 커밋을 수집하면 이번달에 잘못 가산되던 문제).

> **증명 테스트**
> - `MockGithubClientTest` — Mock이 결정론적 sha를 반환하는지 (버그를 드러낼 조건 만들기)
> - `CommitDuplicateFetchTest` — 같은 저장소를 두 번 수집해도 점수가 안 부푸는지
>   - **빨간불 확인함**: `expected: 0 but was: 3`
> - `RankingScoreHealTest` — "GT는 점수를 못 내린다"는 규칙 자체를 회귀 방지로 고정
>
> 참고: `batchUpdate`의 반환값은 MySQL `rewriteBatchedStatements` 환경에서
> `SUCCESS_NO_INFO(-2)`로 나와 삽입 건수 집계에 쓸 수 없다. 그래서 사전 조회 방식을 택했다.

### 결함 8. 남의 그룹 "나가기"로 정원이 뚫림

```kotlin
participateRepository.deleteByGroupAndUser(group, user)   // 반환 타입이 Unit
groupRepository.decrementMemberCounter(groupId)           // 무조건 실행
```

Spring Data는 삭제 건수를 돌려주는 반환 타입을 **선택할 수 있게** 해두는데,
이 코드는 아무것도 안 받는 쪽을 골랐다. 그래서 **실패를 성공과 구분할 방법이 사라졌다.**

멤버가 아닌 사람이 탈퇴를 요청해도 카운터가 1 줄어든다. 3번 반복하면 3 줄어들고,
그만큼 정원이 초과 허용된다 — 결함 2에서 공들여 막은 방어가 반대편으로 뚫린다.

**들어올 때는 반환값을 확인했는데(`joinGroup`), 나갈 때는 안 했다.**

> **증명 테스트**: `GroupLeaveTest` (비멤버 예외 + 실멤버 정상 감소)
> **빨간불 확인함**: `Expecting code to raise a throwable.`

### 결함 9. 분산 락을 커밋 전에 풀었음

결함 3의 락 해제가 `@Transactional` 메서드 내부 `finally`에 있었다.
Spring 트랜잭션 프록시는 "메서드 실행 → 반환 → 커밋" 순서라, `finally`는 **COMMIT 전에** 돈다.

그 틈에 두 번째 요청이 락을 잡으면, 아직 커밋되지 않은 INSERT를 못 보고
GitHub을 또 호출하고 랭킹도 또 올린다 — **결함 7이 이 경로로 재발한다.**

**해결**: 락 해제를 이벤트로 바꿔 `@TransactionalEventListener(AFTER_COMPLETION)`으로 미뤘다.
`AFTER_COMMIT`이 아니라 `AFTER_COMPLETION`인 이유는 **롤백 시에도 락이 풀려야** 하기 때문이다.

> **증명 테스트**: `CommitFetchLockReleaseTest` — GitHub 호출이 실패해도 락은 풀린다
>
> 정상 경로의 커밋 전/후 경합은 밀리초 단위라 `sleep`으로는 안정적으로 재현할 수 없다.
> 그 부분은 Spring의 `AFTER_COMPLETION` 계약으로 구조적으로 보장하고,
> `CommitDuplicateFetchTest`가 같은 유저를 연달아 두 번 호출해 간접 검증한다.

### 결함 10. Redis 장애 폴백이 절반만 동작

```kotlin
catch (e: RedisConnectionFailureException) { ... }   // 연결 끊김만 잡음
```

실제 Redis 타임아웃은 `QueryTimeoutException`으로 올라온다. 안 잡히고 그대로 500이 나갔다.
`DataAccessException`으로 넓혀 둘 다 덮었다.

> **증명 테스트**: `RankServiceFallbackTest` (연결실패 / 타임아웃 / 정상 / 토글 off)
> **빨간불 확인함**: 연결실패·정상 케이스는 기존 코드로도 통과하고 **타임아웃만 정확히 실패**했다.

### 결함 11. 다중 그룹 참여가 조용히 잘림

`participate` 스키마는 한 유저가 여러 그룹에 속하는 걸 허용하는데,
조회는 `participations.first()`로 첫 그룹만 반환했다. 두 번째부터는 사라진다.

**스키마가 과했던 게 아니라 조회 로직이 요구사항을 못 따라간 것**이었다.
반환 타입을 목록으로 바꿨다.

> **증명 테스트**: `GroupMultiMembershipTest`

### 결함 12. 그룹 생성 응답의 memberCount가 항상 0

`incrementMemberCounterIfNotFull()`은 벌크 UPDATE라 DB만 바꾸고 Hibernate 세터를 거치지 않는다.
그래서 생성 직후 반환한 `Group` 객체는 증가 전 값(0)을 들고 있었다.
**생성자 본인이 자동으로 멤버가 되는데 응답은 "멤버 0명"이었다.**

증가 후 재조회해서 반환하도록 고쳤다. 이때 1차 캐시가 아니라 DB를 읽게 하려면
`@Modifying(flushAutomatically = true, clearAutomatically = true)`가 필요하다.

> **증명 테스트**: `GroupCreateResponseTest`
> **빨간불 확인함**: `expected: 1 but was: 0`

## Redis 랭킹 — 왜 옮겼고, 무엇을 대가로 치렀나

### 순위의 본질적 비용

"내가 몇 등인가"에 답하려면 나보다 앞선 사람이 몇 명인지 세야 하고, 그러려면 전부 봐야 한다.
DB 방식은 요청마다 이걸 처음부터 다시 한다 — **매번 10만 명의 커밋을 집계하고 정렬한다.**

Redis 방식은 정렬된 순위표를 미리 만들어두고 읽을 때는 위에서 30줄만 본다.
10만 명이든 100만 명이든 읽는 양이 같다.

| 키 | 자료구조 | 내용 |
|---|---|---|
| `rank:commit:{yyyyMM}` | ZSET | userId → 점수. 실시간 `ZINCRBY` |
| `rank:dense:{yyyyMM}` | HASH | **점수 → 등수**. 스케줄러가 사전 계산 |

HASH를 `점수 → 등수`로 잡은 게 핵심이다. `userId → 등수`가 아니라서
같은 점수 10만 명도 엔트리 하나다. 개인 등수 조회가 `HGET` 한 번으로 끝난다.

초기 구현은 "내 점수보다 높은 멤버를 전부 JVM으로 가져와 세는" 방식이었다 —
5만 등이면 4만 9,999건을 힙에 올린다. 그걸 이 구조로 대체했다.

### 측정 결과

→ **[측정-결과.md](측정-결과.md)** (원본: [`bench/results/`](../bench/results/))

변수 하나(`ranking.redis.enabled`)만 바꾼 A/B. 유저 1만/5만/10만.

| 유저 수 | `GET /rank` Redis | `GET /rank` DB | 배수 |
|---|---|---|---|
| 1만 | 2.4 ms | 43.2 ms | 18배 |
| 5만 | 2.6 ms | 202.7 ms | 78배 |
| 10만 | **2.6 ms** | **464.9 ms** | **179배** |

유저를 10배 늘렸을 때 **Redis는 1.1배, DB는 10.8배** 느려진다.

> **이 측정은 한 번 버리고 다시 했다.** 처음엔 "2,001배"가 나왔는데,
> 그때의 DB 쿼리가 아무도 읽지 않는 컬럼 3개를 조회하고 있었다 — 허수아비를 이긴 셈이다.
> 쿼리를 고치니 8,005ms → 464.9ms가 됐다. 자세한 경위는 측정-결과 문서에 남겼다.
>
> **그리고 `DENSE_RANK()`는 병목이 아니었다.** 윈도우 함수 비용은 실측 9ms, 전체의 2%다.
> 이전 문서는 "DENSE_RANK의 O(N log N) 병목"이라고 적었으나 정확하지 않다.
> 진짜 비용은 **매 요청마다 이번 달 커밋 전체를 집계하는 것**이다.

### 대가 — 같은 사실이 두 곳에 있다

Redis는 공짜가 아니다. "누가 몇 개 풀었나"가 DB와 Redis 두 곳에 존재하게 되고,
**두 곳에 있는 것은 반드시 어긋난다.** 그래서 맞추는 장치가 필요하다.

| 장치 | 역할 |
|---|---|
| `@TransactionalEventListener(AFTER_COMMIT)` + `ZINCRBY` | 커밋 저장 후 실시간 갱신. DB 롤백 시 미반영 |
| 스케줄러 (매시간) | DB를 세어 Redis 보정 |
| ZADD GT (Lua) | 보정이 실시간 증분을 덮어쓰지 않게 |
| Shadow Key + `RENAME` | 등수 HASH 재계산 시 조회 공백 없이 원자적 교체 |
| `DataAccessException` 폴백 | Redis 장애 시 DB 경로로 |

**결함 7은 바로 이 장치들 사이에서 났다.** 성능을 얻는 대가로 정합성 문제를 샀고,
그 대가를 관리하는 장치끼리 충돌한 것이다.

> **증명 테스트**
> - `RankingSelfHealingSchedulerTest` — 이벤트가 유실돼도 스케줄러 후 Redis = DB
> - `RankPathConsistencyTest` — Redis 경로와 DB 폴백이 같은 랭킹을 반환

## 알고 있으나 하지 않은 것

몰라서 안 한 것과 판단해서 뺀 것은 다르다. 여기 적는다.

### ★ 집계 테이블 대신 Redis를 쓴 것

**가장 먼저 나올 질문이다: "집계 테이블 하나 두면 되는데 왜 Redis죠?"**

MySQL에서도 같은 복잡도를 낼 수 있다. B-Tree 인덱스가 곧 정렬을 유지하는 자료구조다.

```sql
CREATE TABLE user_monthly_score (
    user_id    BIGINT,
    year_month CHAR(6),
    score      INT NOT NULL,
    PRIMARY KEY (user_id, year_month),
    INDEX idx_rank (year_month, score DESC)   -- ZSET 스킵리스트에 대응
);
-- 갱신: UPDATE ... SET score = score + ?   (원자적, ZINCRBY 와 동형)
-- 조회: ORDER BY score DESC LIMIT 30       (인덱스 훑기, O(log N + 30))
```

핵심은 인덱스가 아니라 **"집계 결과를 행으로 저장한다"** 는 점이다.
지금은 요청마다 `commits` 205만 행을 세지만, 집계 테이블은 유저당 1행에 이미 센 값이 들어 있다.

#### 그리고 이쪽이 더 안전했을 것이다

결함 7(랭킹 이중 계상)은 **두 저장소를 둔 대가**였다.

| 결함 7의 구성 요소 | 집계 테이블이었다면 |
|---|---|
| ① 요청 개수를 그대로 더함 | **여전히 가능** — 같은 실수를 할 수 있다 |
| ② GT가 하향 보정을 막아 **영구화** | **없음** — GT라는 장치 자체가 불필요 |
| DB와 Redis가 어긋남 | **구조적으로 불가능** — 진실의 원천이 하나 |

게다가 단일 저장소에는 증분 대신 **절대값으로 쓰는** 선택지가 있다.

```sql
UPDATE user_monthly_score
SET score = (SELECT COUNT(*) FROM commits WHERE user_id = ? AND ...)
```

같은 트랜잭션 안에서 정확한 값을 다시 세므로 어긋날 여지가 없다.
Redis에서는 이걸 할 수 없다 — 매번 DB를 세야 하니 오프로딩의 의미가 사라진다.

#### 두 쿼리는 성격이 다르다

**상위 30 조회** — 집계 테이블로 충분하다. 인덱스 위에서 30행만 훑으면 끝이고 Redis와 동급이다.

**개인 등수 조회** — 여기가 갈린다.

```sql
-- 집계 테이블: 나보다 점수 높은 사람을 센다
SELECT COUNT(*) + 1 FROM user_monthly_score WHERE year_month = ? AND score > ?
```

**꼴찌에 가까울수록 세야 할 행이 많아진다.** 9만 9천 등이면 9만 9천 개를 센다.
Redis는 `점수 → 등수` HASH를 미리 구워둬 `HGET` 한 번, `O(1)`이다.

> 다만 그 HASH도 MySQL 테이블로 만들 수 있다(`score → rank` 매핑 저장).
> **진짜 아이디어는 "등수를 미리 계산해둔다"이고, Redis냐 MySQL이냐는 저장 위치 선택이다.**

#### 그래서 Redis는 언제 쓰나

| 상황 | 판단 |
|---|---|
| 랭킹 조회 수백 req/s, 유저 수만 명 | **집계 테이블.** Redis 불필요 |
| 랭킹이 메인 화면이고 수천 req/s | 집계 테이블 + 짧은 TTL 캐시를 먼저 |
| DB가 쓰기로 이미 바빠 **읽기를 떼어내야** 함 | Redis 검토 |
| 앱 서버 여러 대가 **공유 상태**를 봐야 함 | Redis 검토 |
| 이미 Redis를 다른 용도로 운영 중 | Redis 검토 |

측정 수치로 감을 잡으면 — Redis가 13,692~23,865 req/s를 냈다.
집계 테이블은 측정하지 않았으나 인덱스 30행 조회라 수천 req/s는 무리 없이 나올 것이다.
**즉 집계 테이블 대비로는 179배가 아니라 수 배 수준일 가능성이 크다.**

**이 프로젝트 규모(유저 10만, 랭킹이 메인 화면도 아님)에서는 집계 테이블이 맞았다.**
Redis를 고른 것은 "이기종 저장소 간 정합성"을 다뤄보려는 학습 목적이 컸고,
그 대가로 결함 7의 영구화 문제를 겪었다. 그 경험 자체는 남았다.

#### 측정의 한계와도 연결된다

[측정-결과.md](측정-결과.md)의 비교는 **Redis vs "원본에서 매번 집계하는 DB"** 였다.
**"집계 테이블을 둔 DB"와는 비교하지 않았다.** 그쪽이었다면 179배 차이는 나지 않는다.
안 쓰는 컬럼을 조회하던 쿼리와 비교했던 것과 같은 종류의 한계다.

### 스키마 마이그레이션 도구 (Flyway)

`ddl-auto: validate`를 쓰므로 스키마는 `infra/init.sql`을 손으로 관리한다.
엔티티를 바꾸면 같이 고쳐야 하고, 안 고치면 부팅이 막힌다(실제로 두 번 겪음).

**넣지 않은 이유**: 이번 범위에 스키마 변경이 없고, Flyway도 마이그레이션 SQL은 손으로 쓴다.
"엔티티 바꾸면 자동 생성"이 아니다. 대신 Testcontainers가 **운영과 같은 `init.sql`을 그대로**
써서 테스트하므로, 엔티티와 스키마가 어긋나면 서버를 띄우지 않아도 테스트가 잡아낸다.

> 주의: `validate`는 컬럼·타입만 검사하고 **UNIQUE·인덱스는 검증하지 않는다.**
> 실제로 `User` 엔티티에 `uk_users_github_id` 선언이 빠져 있는데 부팅은 정상이다.

### 개인 등수에 `RANK` 대신 `DENSE_RANK`

커밋 수는 값의 종류가 적어서(예: 1~40) `DENSE_RANK`를 쓰면 등수가 압축된다.
**유저 10만 명 중 꼴찌가 "40등"으로 표시된다.** `RANK`였다면 약 9만 7천 등이다.

상위 30명 목록은 동점이 적어 차이가 거의 없지만, `GET /rank/users`(내 등수)에서는
실제보다 좋아 보인다.

**바꾸지 않은 이유**: 두 경로(Redis/DB)가 현재 `DENSE_RANK`로 일관돼 있고 그 일관성이
테스트로 고정돼 있다. 바꾸려면 양쪽을 함께 손봐야 하고, 그러면 측정과 테스트를 다시 봐야 한다.

**바꾼다면**: `score → rank` HASH 구조는 그대로 쓸 수 있다.
`RANK` = 나보다 점수 높은 **사람 수** + 1, `DENSE_RANK` = 나보다 높은 **점수 종류 수** + 1.
둘 다 점수만 알면 정해지는 값이라 자료구조 변경 없이 계산식만 바꾸면 된다.

### Redis 장애가 길어질 때의 대책

폴백은 동작하지만 견디는 범위가 있다.

| 규모 | 폴백 상태 (동시 30명) |
|---|---|
| 유저 1만 | 견딤. 102 req/s, 실패 0% |
| 유저 5만 | 느리지만 버팀. 18.6 req/s, 실패 0%, p95 1.84초 |
| 유저 10만 | 한계. 6.1 req/s, 실패 2.84%, p95 9.36초 |

랭킹을 degrade해서 내보내기, 요청 차단, Redis 이중화는 **범위에 넣지 않았다.**
"폴백이 있으니 괜찮다"가 아니라 **"1만 규모까지 여유가 있고 그 이상은 대책이 없다"**가 정확한 상태다.

### 인증

`SecurityConfig`는 `permitAll()`이고 `userId`를 요청 파라미터로 받는다.
BCrypt를 쓰려고 spring-security 의존성만 넣은 상태다.
Flask 레거시와 동일하며, 이번 범위에서 다루지 않았다.
