# 삭제 명세 — 유저와 그룹

지금까지 이 규칙은 커밋 메시지·계획서·코드 주석에 흩어져 있었다. 한곳에 모은다.

**적용 시점**: 2026-08-20 (`9b3b90e`)
**검증**: `UserLifecycleApiTest`, `UserDeactivationApiTest`, `GroupLeaveTest`

---

## 1. 상태

유저는 두 상태만 갖는다. 물리 삭제 경로는 **없다**.

```
        POST /users (신규)
              │
              ▼
        ┌───────────┐   DELETE /users/delete    ┌────────────┐
        │  active   │ ────────────────────────▶ │  inactive  │
        │  (활성)   │ ◀──────────────────────── │  (탈퇴)    │
        └───────────┘   POST /users (같은 githubId)└──────────┘
```

`users.active BOOLEAN` 이 상태를 들고 있다. 행은 지워지지 않는다.

그룹은 다르다 — 마지막 멤버가 나가면 **행이 실제로 삭제된다**(`GroupService.leaveGroup`).
빈 그룹이 남으면 아무도 지울 수 없기 때문이다(Flask 에 있던 동작을 복원한 것).

---

## 2. 탈퇴가 하는 일 — 테이블별

`DELETE /users/delete?userId=` → `UserService.deleteUser`. 전부 **한 트랜잭션**이다.

| 테이블 | 처리 | 왜 |
|---|---|---|
| `users` | `active = false`. **행 유지** | 재가입 시 같은 유저로 돌아오려면 행이 있어야 한다 |
| `participate` | **행 삭제** (모든 그룹) | 안 지우면 탈퇴자가 정원을 계속 먹는다(유령 멤버) |
| `groups.member_counter` | 나간 만큼 감소 | `participate` 의 파생값이라 같이 움직여야 한다 |
| `groups.owner_id` | 오너였다면 **최고참 멤버에게 승계** | 안 하면 비활성 오너만 남아 아무도 그룹을 관리 못 한다 |
| `groups` | 마지막 멤버였다면 **그룹 삭제** | 빈 그룹은 아무도 못 지운다 |
| `user_monthly_score` | **전 기간 행 삭제** | 랭킹 쿼리에 `active` 필터가 없다 — 행이 없는 것이 곧 제외다 |
| `commits` | **보존** | GitHub 이 원본이다. 재가입 시 점수를 여기서 복구한다 |
| `history` | **보존** | 위와 같다 |

그룹 탈퇴는 `GroupService.leaveGroup` 을 그대로 호출한다. 승계와 빈 그룹 삭제가 거기 있고,
`UserService` 에서 다시 구현하면 두 경로가 갈라진다 — 이 저장소가 반복해 물린 실패다.

### 즉시 눈에 보이는 결과

| 무엇 | 탈퇴 직후 |
|---|---|
| `GET /rank` | 목록에서 사라지고 **남은 사람 순위가 당겨진다** (dense rank 재계산) |
| `GET /rank/users?userId=` | `{"rank": null}` |
| `GET /group/info` | 멤버 목록에서 사라진다 |
| 그룹 정원 | 한 자리 비어 새 멤버가 들어올 수 있다 |
| `GET /users?userId=` | 여전히 조회된다 (`active: false`) |

---

## 3. 재가입

같은 `githubId` 로 `POST /users` → **재활성화 + 점수 복구**.

| 대상 | 복구되나 |
|---|---|
| `users.active` | ✅ `true` 로 |
| `user_monthly_score` | ✅ `commits` 에서 다시 계산 (`backfillFromCommits`) |
| `commits` · `history` | ✅ 지운 적이 없다 |
| `user_id` | ✅ 같은 값 유지 |
| **그룹 참여** | ❌ **복구 안 됨. 다시 참여해야 한다** |

그룹만 복구하지 않는 이유: 남은 멤버 입장에서 **모르는 사이에 사람이 돌아와 있으면 곤란하다.**
그룹은 다른 사람들과의 관계라 한쪽 의사만으로 되돌릴 수 없다.

랭킹에는 즉시 복귀한다 — 커밋이 남아 있으므로 점수가 그대로 재현된다.

---

## 4. 점유가 유지되는 것

탈퇴해도 **반납되지 않는다.**

| 값 | 제약 | 탈퇴 후 |
|---|---|---|
| `users.github_id` | `UNIQUE` | 계속 점유. 남이 같은 GitHub 계정으로 가입 불가 |
| `users.nickname` | `UNIQUE` | 계속 점유. 남이 같은 닉네임 사용 불가 |

재활성화 경로가 있으므로 **본인이 다시 쓴다**는 전제다. 반납하면 재가입 시 닉네임을
새로 정해야 하고, `github_id` 는 반납하는 순간 재가입 자체가 불가능해진다.

---

## 5. 불변조건과 시행 지점

| 불변조건 | 누가 지키나 | 강도 |
|---|---|---|
| 비활성 유저는 `user_monthly_score` 행이 없다 | `deleteUser` + `CommitService` 의 `if (user.active)` 가드 | ⚠️ **앱 코드만** |
| 비활성 유저는 `participate` 행이 없다 | `deleteUser` | ⚠️ **앱 코드만** |
| `member_counter` == `participate` 실제 개수 | 원자적 조건부 `UPDATE` | ⚠️ **대사(reconciliation) 없음** |
| 한 유저는 한 그룹에 한 번만 | `uk_participate_group_user` | ✅ **DB** |
| 유저당 sha 는 하나 | `uk_commits_user_sha` | ✅ **DB** |

**⚠️ 표시가 이 명세의 약한 고리다.** DB 가 막아주지 않으므로 새 쓰기 경로가 생기면
조용히 깨진다. 랭킹 성능(50k 기준 87ms → 0.5ms)을 위해 읽기 조인을 없앤 대가이고,
지금은 위 테스트들이 유일한 방어다.

## 6. 아직 정하지 않은 것

**이 절이 비어 있지 않다는 게 중요하다.** 정한 척하는 것보다 낫다.

### 6-1. 보관 기간 — 정해진 바 없음

지금은 **무기한**이다. 탈퇴한 유저의 `users` 행, `commits`, `history` 가 영원히 남는다.
의도적으로 고른 게 아니라 **아무도 정하지 않아서 그렇게 된 것**이다.

정해야 할 것:
- 탈퇴 후 N개월이 지나면 물리 삭제하는가?
- `commits` 는 GitHub 공개 데이터의 사본이라 성격이 다른가?
- `github_id`·`nickname`·`repository_name` 은 개인을 식별할 수 있다 — 보관 근거가 필요한가?

### 6-2. 물리 삭제 경로 없음

"내 데이터를 완전히 지워달라"에 응할 수단이 지금 **없다**. 소프트 삭제만 있다.
`commits` 에 FK 가 걸려 있어 물리 삭제하려면 삭제 순서를 정하거나 `ON DELETE` 정책을
바꿔야 한다(현재 `RESTRICT`, Alembic 시절은 `CASCADE` — 두 스키마가 어긋난 채로 남아 있다).

### 6-3. 비활성 유저의 커밋이 그룹 랭킹에 남는가

`findMemberCommits` 는 `participate` 에서 뽑은 `memberIds` 로 조회한다. 탈퇴 시
`participate` 행을 지우므로 **자동으로 빠진다.** 다만 이건 설계로 정한 규칙이 아니라
`participate` 삭제의 부수 효과다. 지금은 `UserLifecycleApiTest` 의 "탈퇴한 사용자는 그룹
멤버 목록에서 사라진다"가 결과만 고정하고 있다 — 규칙으로 승격할지는 정하지 않았다.

### 6-4. 대사(reconciliation) 부재

`member_counter` 가 실제와 어긋나도 감지할 방법이 없다. `PLAN-db-foundation.md` Phase 5 에
CHECK 제약과 함께 다루기로 미뤄져 있다.
