# 코테독촉기 — 만들고, 과하게 키우고, 되돌아본 기록

GitHub 저장소의 백준 풀이 커밋을 모아 월별 랭킹을 매기는 서비스.
대학교 4학년 학교 프로젝트로 Flask로 처음 만들었고, 나중에 Kotlin + Spring Boot로 옮겼다.

**기능은 조회·정렬·삽입·삭제가 전부다.**

---

## 한 문장으로

> 필요 없는 복잡도를 넣었고, 거기서 버그가 나왔고, 측정해보니 그 복잡도가 애초에 필요 없었다.

이 문서는 그 과정의 기록이다. 잘한 것보다 **틀린 것을 더 자세히 적었다.**

---

## 왜 Flask로 시작했고, 왜 Kotlin으로 옮겼나

**Flask였던 이유**: Swift를 배우는 수업의 프로젝트라 백엔드까지 새로 배울 여유가 없었다.
아는 언어가 파이썬이어서 Flask를 골랐다. 그 이후로 Flask를 다시 쓴 적은 없다.

**Kotlin으로 옮긴 이유**: **백엔드 취업 준비.** 국내 시장에서 Spring이 사실상 표준이라
배워야 했고, 새 주제를 잡는 대신 기존 프로젝트를 소재로 삼았다.

**제품상 필요는 없었다.** Flask 앱은 인덱스 문제를 고친 뒤 p95 86ms로 잘 돌고 있었다.

> "확장성을 대비해 옮겼다"고 쓸 수도 있었지만 사실이 아니다.
> 유저가 수백 명인 서비스에 확장성은 이유가 되지 않는다.
> 취업 준비라는 이유 자체에는 문제가 없다. 그걸 다른 말로 바꾸는 게 문제다.

**그래도 남은 것**: 한 줄씩 다시 쓰다 보니 "이건 왜 이렇게 되어 있지?"를 계속 묻게 됐다.
결함이 나온 건 Kotlin이라서가 아니라 **다시 썼기 때문**이고, Flask에서도 할 수 있었다.

## 과했던 것 (먼저 인정)

### Redis 랭킹

이 시기에 MSA와 캐싱을 배우고 있었고, "랭킹은 Redis"라는 말을 자주 들었다. 그래서 넣었다.

**직접 측정해보니 필요 없었다.**

| 유저 수 | DB만으로 `GET /rank` | 판단 |
|---|---|---|
| 1만 | **45 ms** | 전혀 문제 없음 |
| 5만 | 211 ms | 체감되지만 견딤 |
| 10만 | 480 ms | 이제야 아쉬움 |

실사용자가 수십~수백 명인 서비스다. **랭킹 쿼리는 밀리초 단위로 끝난다.**

### 게다가 Redis가 최선도 아니었다

MySQL에서도 같은 복잡도가 나온다. B-Tree 인덱스가 곧 정렬을 유지하는 자료구조다.

```sql
CREATE TABLE user_monthly_score (
    user_id BIGINT, year_month CHAR(6), score INT NOT NULL,
    PRIMARY KEY (user_id, year_month),
    INDEX idx_rank (year_month, score DESC)
);
-- 갱신: UPDATE ... SET score = score + ?    (ZINCRBY 와 동형)
-- 조회: ORDER BY score DESC LIMIT 30        (O(log N + 30))
```

핵심은 인덱스가 아니라 **"집계 결과를 행으로 저장한다"**는 점이다.
지금은 요청마다 `commits` 205만 행을 세지만, 집계 테이블은 유저당 1행에 이미 센 값이 들어 있다.

**그리고 이쪽이 더 안전했다** — 진실의 원천이 하나라 아래 이야기 ②의 문제가 애초에 안 생긴다.

Redis가 값을 하는 건 읽기 부하를 DB에서 떼어내야 할 때, 앱 서버 여러 대가 공유 상태를 볼 때다.
**이 프로젝트는 둘 다 아니었다.**

## 결함 12개 — 어디서 왔나

이전 버전 문서는 "레거시 결함 11개를 발견해 고쳤다"고 적었다. **절반만 사실이다.**

| 출처 | 결함 |
|---|---|
| **Flask에 원래 있던 것** | 정원 Lost Update / Clock 테스트 불가 / leaveGroup 카운터(그대로 옮겨옴) / 단건 upsert 루프 |
| **Kotlin에서 내가 만든 것** | 랭킹 이중 계상 · 락 해제 순서 · Redis 폴백 반쪽 · 그룹 생성 응답 0 |
| **Kotlin에서 퇴보시킨 것** | **다중 그룹 조회** — Flask는 목록을 제대로 반환했는데 `.first()`로 잘라먹음<br>**스키마 마이그레이션 도구** — Flask에는 Alembic이 있었는데 대체물 없이 사라짐 |
| 포팅 적응 · 스타일 | 복합키→대리키 / 분산 락 신규 도입 / Native Query 정리 |

**마이그레이션이 만든 게 더 많다.** 특히 다중 그룹은 Flask가 더 잘하던 걸 망가뜨린 것이다.

이 표를 앞에 둔 이유는 간단하다. `app/` 의 Flask 코드를 열어보면 확인할 수 있는 사실이고,
**문서가 코드와 다르면 문서 전체를 믿을 수 없게 된다.**

## 세 가지 문제

셋은 각각 다른 문제다. 섞어서 설명하면 어느 것도 정확해지지 않는다.

### ① 그룹 정원 — Flask에 있던 진짜 버그

```python
if group.member_counter >= group.member_maxCnt:  # 확인 (읽기)
    return error
group.member_counter += 1                         # 증가 (읽고 → +1 → 쓰기)
```

확인과 증가가 따로 있어서, 동시에 두 명이 들어오면 둘 다 통과한다.

**세 번 시도해서 답을 찾았다.**

| 시도 | 결과 |
|---|---|
| 컬럼 제거, `participations.size` | LAZY 컬렉션 전체 로딩 → OOM 위험 |
| `COUNT` 후 INSERT | 둘이 같은 값을 읽음 → TOCTOU |
| **컬럼 유지 + DB 원자적 조건부 UPDATE** | 해결 |

```sql
UPDATE groups SET member_counter = member_counter + 1
WHERE group_id = ? AND member_counter < member_max_count   -- 반환 1=성공, 0=정원초과
```

**확인과 행동을 한 문장으로 합쳐 그 사이의 틈을 없앴다.**

깨지는 방식이 두 가지라는 것도 구분해야 한다.

| | 무엇이 틀리나 |
|---|---|
| Flask 원본 | 둘 다 4를 읽고 둘 다 5를 씀 → **카운터가 실제보다 작음** |
| 재현용 TOCTOU 버전 | DB는 거절(0 반환)했는데 코드가 무시 → **참가자 행이 정원 초과** |

> **직접 재현함**: 정원 1자리에 20명 동시 요청 → `expected: 1 but was: 8`
> 실행할 때마다 숫자가 달라진다(7, 8, …). 스레드 스케줄링에 따라 몇 명이 낡은 값을 보는지가
> 바뀌기 때문이다. **재현이 일정하지 않아 로컬에서 몇 번 돌려보는 것만으로는 놓치기 쉽다.**
>
> 증명: `GroupJoinConcurrencyTest` (동시 20명 + 자리 충분할 때 전원 성공 대조군)

### ② 랭킹 정합성 — 내가 만든 버그. 복잡도의 대가

**이건 레거시 결함이 아니다.** Flask엔 Redis가 없었으니 존재할 수 없었다.

커밋 수집 흐름:
1. GitHub에서 커밋 5개를 받는다
2. DB에 저장 — `ON DUPLICATE KEY UPDATE`라 이미 있는 건 건너뜀 (실제 2건만 삽입)
3. 랭킹 점수를 올린다 — **"5점"을 그대로 더했다**

그런데 매시간 도는 자가 치유 스케줄러가 이걸 못 고친다.
**ZADD GT**(GT = greater than, "기존 값보다 클 때만 갱신") 때문에 **점수를 올릴 수만 있다.**

```
Redis 15점 / DB 5개
스케줄러: "5는 15보다 작으니 안 바꿈"  → 영구히 15점
```

```
① 요청 개수를 그대로 더함 → 점수가 부품
② GT가 하향 보정을 막음   → 영구화

①만 있으면 스케줄러가 1시간 안에 고침. ②만 있으면 부풀 일이 없음. 둘 다여서 영구 오류.
```

**왜 못 찾았나** — 부하 테스트용 Mock이 호출할 때마다 새 UUID를 sha로 만들었다.
중복이 구조적으로 발생할 수 없어 이 버그가 나타날 방법이 없었다.

**해결** — GT는 그대로 뒀다. 빼면 Lost Update가 돌아온다.
대신 **증분을 정확하게** 만들었다: 삽입 전 기존 sha를 조회해 실제 신규 커밋만 반영하고,
버킷도 서버의 "지금"이 아니라 각 커밋의 실제 날짜 기준으로 나눴다.

> **빨간불 확인**: `expected: 0 but was: 3`
> 증명: `MockGithubClientTest`, `CommitDuplicateFetchTest`, `RankingScoreHealTest`

**집계 테이블이었으면 없었을까** — 통째로는 아니다.
① 요청 개수를 그대로 더하는 실수는 거기서도 가능하다. 사라지는 건 ② 영구화되는 부분이다.
게다가 단일 저장소면 증분 대신 **절대값**(`SET score = (SELECT COUNT(*) ...)`)으로 쓸 수 있어
어긋날 여지 자체를 없앨 수 있다. Redis에서는 불가능하다.

### ③ 성능 — 측정이 오히려 "과했다"를 보여줬다

변수 하나(`ranking.redis.enabled`)만 바꾼 A/B. 재현: `bash bench/run.sh`

아래는 **2026-08-03 측정**이다. `findUserRank`를 고친 뒤 처음 잰 값이라,
두 경로가 같은 답을 내는 상태에서 잰 첫 측정이다(사유는 바로 아래).

**동시성 1** (커넥션 풀 경합이 없는 조건 — 순수 쿼리 비용):

| 유저 수 | | Redis | DB | 배수 |
|---|---|---|---|---|
| 1만 | `/rank` (top30) | 3.0 ms | 44.6 ms | 15배 |
| | `/rank/users` (개인) | 3.4 ms | 54.2 ms | 16배 |
| 5만 | `/rank` | 2.7 ms | 210.5 ms | 78배 |
| | `/rank/users` | 4.0 ms | 216.4 ms | 54배 |
| 10만 | `/rank` | 2.7 ms | **480.1 ms** | **178배** |
| | `/rank/users` | 2.8 ms | **496.3 ms** | **177배** |

**VU 30, 60초** (실제 부하):

| 유저 수 | Redis | DB |
|---|---|---|
| 1만 | 20,744 req/s, 실패 0% | 100.4 req/s, 실패 0% |
| 5만 | 12,480 req/s, 실패 0% | 14.4 req/s, 실패 0% |
| 10만 | 10,817 req/s, 실패 0% | 6.9 req/s, **실패 4.13%** |

유저를 10배 늘렸을 때 **Redis는 평평하고(3.0 → 2.7 ms), DB는 10.8배**로 늘었다.
기울기가 다르다는 건 세 번 재는 동안 한 번도 안 바뀌었다.

**그런데 이 서비스는 1만 명 근처에도 못 간다.** 44.6 ms면 충분하다.

#### 이 표는 세 번째 측정이다

앞의 두 번은 **두 경로가 같은 답을 내지 않는 상태**에서 잰 것이었다.
`findUserRank`가 `LEFT JOIN`이라 이번 달 커밋이 0건인 유저도 순위를 받았고,
Redis 경로는 같은 유저에 `null`을 줬다. `/rank/users`를 재던 A/B가
**등가가 아닌 두 구현을 비교하고 있었다.**

더 나쁜 건 그걸 알고 고친 뒤에도(`51abeb7`) **재측정을 안 했다는 것**이다.
커밋 메시지에는 적어놨는데 문서의 표는 아무 표시 없이 그대로 남아 있었다.

`bench/results/`도 정리했다. 이전에는 **서로 다른 실행에서 나온 파일이 섞여 있었다** —
`summary.txt`는 5만 규모에서 죽은 부분 실행(실패율 83%)이 덮어써 3줄만 남아 있었고,
`10000_*.json`은 그 실행 것, `100000_*.json`은 그 전 실행 것이었다.
문서의 표는 어느 쪽과도 일치하지 않았다. 지금은 전부 한 번의 실행에서 나온 것이다.

#### 이 측정은 한 번 버리고 다시 했다

처음엔 **2,001배**가 나왔다. 그때 DB 쿼리가 **아무도 읽지 않는 컬럼 3개**
(`githubId`, `nickname`, `previousMonthCount`)를 조회하고 있었다.
안 쓰는 VARCHAR 둘이 `GROUP BY` 키를 넓히고 조인 범위를 2개월로 늘렸다.

**비교 대상이 잘못 만들어져 있었다.** MySQL에서 쿼리만 직접 재보면 이렇다
(유저 10만, 3회 측정):

| 쿼리 | 시간 |
|---|---|
| 당시 `findTop30Rank` | **4,882 ms** |
| 안 쓰는 컬럼만 제거 (`DENSE_RANK` 유지) | **531 ms** |
| 거기서 `DENSE_RANK`까지 제거 | 522 ms |

**9.2배가 안 쓰는 컬럼 탓이었다.**
그리고 **`DENSE_RANK()`는 병목이 아니었다** — 윈도우 함수 비용은 **9ms, 전체의 2%**다.
진짜 비용은 매 요청 전체 집계다.

> 측정을 시작하기 전에 **비교 대상이 제대로 만들어졌는지 먼저 확인해야 한다.**
> 그러지 않으면 상대를 이긴 게 아니라 내가 만든 비효율을 이긴 것이 된다.

#### 남은 한계 — 절대값은 믿지 말 것

**같은 스크립트로 두 번 재봤더니 DB 쪽 절대값이 2배 가까이 달랐다.**

| | 1차 | 2차 | 3차 (현재 표) |
|---|---|---|---|
| 1만 DB `rank` | 43.2 ms | 84.0 ms | 44.6 ms |
| 10만 DB `rank` | 464.9 ms | 990.2 ms | 480.1 ms |

로컬 단일 머신에서 앱·MySQL·Redis·k6가 자원을 나눠 쓰고, 각 조건을 한 번씩만 쟀다.
**규모 간 기울기 비교만 의미가 있고, 절대값은 환경에 종속적이다.**
세 번 모두 Redis는 평평했고 DB는 유저 수에 비례했다 — 결론은 같았다.
배수는 268배에서 178배로 내려갔지만 **"이 규모에서는 과했다"는 결론은 그대로다.**

그리고 이 비교는 **Redis vs "원본에서 매번 집계하는 DB"**였다.
**"집계 테이블을 둔 DB"와는 비교하지 않았다.** 그쪽이었다면 수백 배가 아니라 수 배 수준일 것이다.

## Redis가 죽으면

`ranking.redis.enabled=false`가 곧 장애 폴백 경로다. 그래서 이 측정 하나가 그 답도 준다.

| 규모 | 폴백 상태 (동시 30명) |
|---|---|
| 유저 1만 | 견딤. 100.4 req/s, 실패 0% |
| 유저 5만 | 버티지만 느리다. 14.4 req/s, 실패 0% |
| 유저 10만 | 한계. 6.9 req/s, **실패 4.13%** |

**"짧은 장애는 버티지만 길어지면 대책이 없다"**가 정확한 답이다.
랭킹 degrade, 요청 차단, Redis 이중화는 범위에 넣지 않았다.

## 테스트 74개

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
cd server && ./gradlew test
```

Testcontainers로 **실제 MySQL·Redis**를 띄운다. H2나 임베디드 Redis를 쓰면
검증 대상(InnoDB row lock, Redis Lua 원자성)이 사라져 테스트가 의미를 잃는다.

운영과 **같은 `infra/init.sql`**을 그대로 써서, 엔티티와 스키마가 어긋나면
서버를 띄우지 않아도 테스트가 잡는다.

| 테스트 | 무엇을 증명하나 |
|---|---|
| `GroupJoinConcurrencyTest` | 정원 1자리에 20명 → 정확히 1명 (+ 대조군) |
| `GroupLeaveTest` | 비멤버 탈퇴로 카운터가 안 내려감 |
| `GroupMultiMembershipTest` | 다중 그룹이 전부 반환됨 |
| `GroupCreateResponseTest` | 생성 응답의 memberCount가 1 |
| `GroupValidationTest` | 비밀번호·그룹명 trim 이 생성·참여 양쪽에서 대칭 |
| `MockGithubClientTest` | Mock이 결정론적 sha 반환 (버그 재현 조건) |
| `CommitDuplicateFetchTest` | 재수집해도 랭킹이 안 부품 |
| `CommitFetchLockReleaseTest` | 예외가 나도 분산 락은 풀림 |
| `ClockInjectionTest` | `Clock.fixed()`로 특정 시점 재현 |
| `RankingScoreHealTest` | GT가 하향 보정을 막는다는 규칙 고정 |
| `RankingSelfHealingSchedulerTest` | 이벤트 유실 후 스케줄러가 Redis=DB 복원 |
| `RankServiceFallbackTest` | 연결 실패·타임아웃 모두 DB 폴백 |
| `RankPathConsistencyTest` | Redis 경로와 DB 폴백이 같은 랭킹 (Top30 + 폴백 시점) |

HTTP 계층 — `ApiTest`를 상속해 실제 서버를 띄우고 요청을 보낸다.

| 테스트 | 무엇을 증명하나 |
|---|---|
| `GroupApiTest` | 상태코드·응답 본문·`@Valid` (아래) |
| `GroupPasswordApiTest` | 오너가 아니면 비밀번호를 못 바꾸고, 거부 후 기존 비번이 그대로 |
| `GroupMemberApiTest` | 중복 참여·순차 정원 초과 거부 + 거부 후 인원수 불변 |
| `GroupIsolationApiTest` | 남의 그룹이 내 조회에 안 섞임 (+ 같은 그룹은 서로 보임) |
| `UserApiTest` | 로그인 멱등성(같은 githubId=같은 userId), 닉네임 중복 409 |
| `NotFoundApiTest` | 없는 자원 404, 파라미터 누락·타입 불일치 400 |
| `RankApiTest` | 응답 모양, `DENSE_RANK` 동점, 순위 없음이 JSON `null` |

> 테스트를 먼저 깔아둔 게 값을 한 순간이 있다. `@Modifying`에 `clearAutomatically`만 넣고
> `flushAutomatically`를 빠뜨렸더니 **탈퇴가 DB에 반영되지 않는 회귀**를 만들었는데,
> `GroupLeaveTest`가 같은 세션에서 즉시 잡았다.

### 테스트가 전부 통과하는데 서버는 고장나 있었다

푸시 직전에 서버를 띄워 직접 눌러봤다. **버그 여섯 개가 나왔다.**
테스트 35개는 그때 전부 초록불이었다.

원인은 하나다. 그 35개가 **전부 서비스를 직접 호출**하고 있었다.

```kotlin
groupService.joinGroup(userId, groupId, password)   // 기존 35개
```

DB 와 Redis 는 Testcontainers 로 진짜를 띄웠는데, 정작 **웹 계층만 통째로 빠져 있었다.**
그래서 이 계층에만 사는 것들이 하나도 검증되지 않았다:

- `@Valid` — 컨트롤러 파라미터에 붙는다. 서비스를 직접 부르면 아예 실행되지 않는다
- 예외 → 상태코드 매핑 — `@RestControllerAdvice` 가 잡는다
- 응답 본문과 직렬화 결과

찾은 여섯 개 중 넷이 정확히 이 계층 것이었다:

| 증상 | 원인 |
|---|---|
| 빈 그룹명 → 500 | `spring-boot-starter-validation` 은 의존성에 있었지만 어디에도 안 붙어 있었다 |
| 중복 그룹명 → 500 | UNIQUE 위반이 그대로 올라감 |
| 생성 응답 `memberCount` 가 0 | 벌크 UPDATE 후 재조회를 안 함 |
| 데모 페이지가 통째로 멈춤 | 본문 없는 201/204 에서 `res.json()` 실패 후 `res.text()` 를 또 불러 `body stream already read` |

그래서 `ApiTest` 를 만들었다. `RANDOM_PORT` 로 서버를 진짜 띄우고 `RestTemplate` 로 부른다.
**의존성은 추가하지 않았다** — `spring-boot-starter-test` 에 전부 들어 있다.

### 그리고 새 테스트도 검증했다

테스트를 썼다고 그게 무언가를 지키고 있다는 보장은 없다.
그래서 **본문 코드를 한 줄씩 일부러 망가뜨려** 각 테스트가 실제로 빨간불이 되는지 봤다.

여기서 내 테스트의 구멍이 하나 나왔다.

```kotlin
// 이 테스트는 참여 쪽 trim 을 지워도 통과했다
생성 " pw123 "  → trim 되어 "pw123" 저장
참여 "pw123"    → trim 이 필요 없음      ← 참여 경로를 안 지남
```

방향을 뒤집은 케이스(생성 `"pw123"` / 참여 `"  pw123  "`)를 추가하고 나서야
참여 쪽 `trim` 을 지웠을 때 빨간불이 났다.

**테스트를 쓰는 것과 그 테스트가 유효한지 확인하는 것은 별개의 일이다.**

### 그다음 — "어느 테스트가 빠졌나"를 사람이 세지 않게 했다

HTTP 테스트를 붙였지만 `GroupApiTest` 하나뿐이었다. 나머지 도메인은 여전히 서비스를
직접 부르고 있었고, **어디가 빠졌는지는 매번 사람이 읽어서 세야 했다.** 셀 때마다
답이 달랐다.

그래서 세지 않고 재기로 했다. `EndpointAudit`이 테스트가 도는 동안 다섯 가지를
기록한다 — 등록된 엔드포인트 전체, 실제로 라우팅된 핸들러, 관측된 상태 코드,
**실제 발생한 예외 타입**, 테스트별 생성 사용자 수.

네 번째가 핵심이다. "소유권 검사가 검증되는가"는 판단이지만
**"`NotGroupOwnerException`이 테스트 중 실제로 발생했는가"는 측정**이다.
같은 질문의 답인데 후자는 매번 같은 값이 나온다.

측정 결과 엔드포인트 19개 중 HTTP 테스트가 닿은 건 5개였다. 심각도 순으로 채웠다.

| 채운 것 | 왜 심각했나 |
|---|---|
| `PATCH /group/password` 오너 검사 | 코드엔 있는데 어느 계층에도 테스트가 없었다. 막아뒀다고 믿었을 뿐 확인한 적이 없어, 그 줄을 지워도 빨간불이 안 났다 |
| `POST /group/member` 중복·정원 | 정원은 동시성 테스트만 있었다. 동시 요청 20개를 던지는 테스트는 "두 번째 사람이 순차로 들어올 때 무슨 코드가 나가는가"를 답하지 않는다 |
| `GET /group/info` 격리 | 기존 테스트는 "내 그룹이 다 나오는가"만 봤다. `findByUser`의 사용자 필터를 지우면 결과가 더 많이 나올 뿐이라 `contains` 단언은 그대로 통과한다 |

그리고 **테스트를 채우다 본문 결함이 하나 나왔다.** 아래 별도 항목.

덤으로 `ApiTest.patch()`가 **원래부터 동작하지 않았다**는 것도 드러났다.
`RestTemplate` 기본 팩토리가 `HttpURLConnection`을 써서 PATCH 를 거부한다.
헬퍼는 있었는데 호출하는 테스트가 없어서 깨진 줄도 몰랐다 —
미검증 구간은 본문 코드에만 생기는 게 아니라 **테스트 하네스에도 생긴다.**

마지막으로 이걸 게이트로 고정했다. `./gradlew test` 뒤에 `verifyEndpointCoverage`가
이어 돌고, 판정 근거는 계측 파일이다. 아직 못 채운 7개는 사유·심각도와 함께
`src/test/resources/endpoint-allowlist.txt`에 적혀 있다. **부채 명세서지 예외 처리가
아니다.** 새 엔드포인트는 목록에 없으므로 자동으로 빨간불이 된다.

### 개인 순위 쿼리가 Redis 경로와 달랐다 — 벤치마크가 성립하지 않고 있었다

`RankApiTest`를 쓰자 두 개가 실패했다. 테스트 버그가 아니었다.

| 이번 달 커밋이 0건인 유저의 `GET /rank/users` | 결과 |
|---|---|
| Redis 경로 | `null` (ZSET에 점수가 없음) |
| DB 경로 | **순위 숫자** |

`findTop30Rank`는 `JOIN`(INNER), `findUserRank`는 `LEFT JOIN` + `SUM(CASE ...)`였다.
Top30 바로 위 주석에 *"INNER JOIN이 두 경로의 결과를 일치시킨다"*고 적어놓고
`findUserRank`에만 적용하지 않았다.

**`bench/rank_ab.js`가 `ranking.redis.enabled`를 켜고 꺼서 두 경로의 지연시간을 A/B로
비교한다. 등가가 아닌 두 구현의 속도를 재고 있었다.** 게다가 벤치는 `MAX_USER_ID`
범위에서 무작위 `userId`를 뽑으므로 커밋 없는 유저를 자주 때린다.

`RankPathConsistencyTest`가 이 불일치를 못 잡은 이유도 분명하다. 그 테스트가 덮는 건
Top30 일치와 "Redis가 비어 있을 때 개인 순위도 DB로 폴백한다" 두 가지인데,
후자는 **커밋이 있는 유저**만 다루고 `isNotNull()`만 단언한다.
커밋 0건 지점이 정확히 빈 곳이었다.

`findUserRank`를 `JOIN`으로 맞췄다. 지금은 두 경로가 실제로 같은 답을 낸다.

## 알고 있으나 하지 않은 것

몰라서 안 한 것과 판단해서 뺀 것은 다르다.

| | 왜 안 했나 |
|---|---|
| **집계 테이블로 되돌리기** | 지금 와서 바꾸면 측정과 테스트를 다시 봐야 한다. **"과했다"는 사실을 기록으로 남기는 쪽**을 택함 |
| **스키마 마이그레이션 도구 복구** | 아래 별도 항목 참조. **누락이 아니라 퇴보다** |
| **개인 등수를 `RANK`로** | 커밋 수는 값의 종류가 적어 `DENSE_RANK`는 등수를 압축한다 — **10만 명 중 꼴찌가 "40등"**. `RANK`면 약 9만 7천 등. 두 경로가 일관돼 있고(위 "개인 순위 쿼리" 항목에서 맞춤) `RankApiTest`가 동점 처리를 고정하고 있어 두었다 |
| **인증** | `permitAll()`이고 `userId`를 요청 파라미터로 받는다. Flask 레거시와 동일 |
| **스키마 개선 6줄** | 설계는 해봤으나(UNIQUE 범위, `solve_time` 타입 등) 적용하지 않음. git 이력에 있음 |

> `ddl-auto: validate`는 컬럼·타입만 검사하고 **UNIQUE·인덱스는 검증하지 않는다.**
> 실제로 `User` 엔티티에 `uk_users_github_id` 선언이 빠져 있는데 부팅은 정상이다.

### 스키마 마이그레이션 도구 — 누락이 아니라 퇴보다

Flask에는 **Alembic이 있었다.** `migrations/versions/` 에 두 개가 남아 있다.

| 리비전 | 내용 |
|---|---|
| `982bf9b83b5e` | initial |
| `a5474dcca4a9` | **add index on commit_date** (2026-03-15) |

두 번째는 위 "① Flask 단계에서 고친 것"의 실제 흔적이다.

**Kotlin으로 옮기면서 대체물 없이 사라졌다.** 지금은 `infra/init.sql` 하나를 손으로 관리한다.

`init.sql`은 Alembic을 대체하려고 만든 게 아니다.
`docker-compose.yml`과 같은 커밋(`36edfb8`, 2026-03-27)에서 생겼고,
목적은 **로컬 MySQL 컨테이너에 테이블을 만드는 것**이었다. 그 용도로는 맞는 선택이다.

문제는 그 뒤로 아무것도 오지 않았다는 것이다.

```
Flask  →  Alembic     스키마 이력 관리
Kotlin →  init.sql    로컬 부트스트랩 ... 그리고 끝
```

**같은 자리를 채운 게 아니라, 다른 용도의 물건이 들어오고 원래 자리는 비었다.**
바로 다음 커밋이 `fix: init.sql 스키마를 엔티티 정의에 맞게 수정`(`38f878b`)인 것이 그 증상이다 —
마이그레이션 도구가 있었으면 "엔티티에 맞춰 손으로 고치는" 작업 자체가 없었다.

#### `init.sql` 방식의 한계

`docker-entrypoint-initdb.d`는 **볼륨이 비어 있을 때 최초 1회만** 실행된다.
새 DB에는 적용되지만 **기존 DB에는 영원히 적용되지 않는다.**
마이그레이션 도구가 아니라 초기 부트스트랩이다.

| | `init.sql` | Alembic / Flyway |
|---|---|---|
| 무엇이 적용됐는지 기록 | 없음 | 버전 테이블 |
| 기존 DB에 증분 적용 | 불가 | 가능 |
| 적용 순서 보장 | 없음 | 있음 |

용도별로 나눠 보면 이렇다.

| 용도 | 판단 |
|---|---|
| 로컬 개발 부트스트랩 | 문제없다. 흔한 방식이다 |
| Testcontainers 테스트 스키마 | 오히려 낫다 — 운영과 같은 파일을 검증하게 된다 |
| **운영 스키마 관리** | **방법이 없다.** 여기가 구멍이다 |

#### 그래도 지금 넣지 않은 이유

Flyway를 도입하면 스택이 하나 늘고 측정·테스트를 다시 봐야 한다.
이 프로젝트에서 반복해 겪은 "복잡도를 늘렸더니 문제가 따라오는" 패턴을 또 한 번 밟는 셈이다.

**대신 무엇을 잃었는지 정확히 적어두는 쪽을 택했다.**
운영에 실제로 스키마를 바꿔야 하는 시점이 오면 그때가 도입할 때다.

`migrations/` 폴더는 지우지 않고 남겨뒀다 — `app/` 을 대조용으로 남긴 것과 같은 이유다.

## 이 프로젝트로 주장하지 않는 것

- **"Kotlin/Spring을 다룰 수 있다"** — 성과가 아니라 시작 조건이다.
- **"Redis 써서 2,001배 빨라졌다"** — 폐기된 숫자다. 비교 대상이 잘못돼 있었다.
- **"레거시 결함을 발견해 고쳤다"** — 절반 이상은 옮기면서 직접 만든 것이다.
- 기술 스택을 더 늘리지 않는다. 지금 있는 것도 과하다.
