레슨 01 · 테스트 경계

포트는 테스트 경계다

GithubClientPort 를 예로, 인터페이스 하나의 위치가 어떤 코드를 검증 가능하게 만들고 어떤 코드를 영영 검증 불가능하게 만드는지 본다.

1. 포트가 무슨 말인가

포트는 애플리케이션이 소유한 인터페이스다. "나는 이런 게 필요하다"를 선언하고, 그걸 어떻게 제공할지는 바깥에 맡긴다. 구현체를 어댑터라 부른다. Alistair Cockburn 이 2005년에 이름 붙인 Ports and Adapters 다. 

GithubClientPort            ← 포트 (인터페이스)
  ├── GithubClient          ← 어댑터: 진짜 api.github.com
  └── MockGithubClient      ← 어댑터: 테스트용

CommitService 는 포트에만 의존한다. 그래서 테스트에서 진짜 GitHub 대신 Mock 을 끼울 수 있다. 이게 포트의 목적이다 — 외부 세계를 갈아 끼울 수 있는 경계.

이 레슨의 핵심 한 줄. 포트의 시그니처는 단순한 함수 선언이 아니라 무엇이 경계를 넘어오는가의 계약이고, 동시에 테스트 더블이 대체할 수 있는 범위의 선이다. 그 선보다 아래에 있는 코드는 그 더블로 테스트할 수 없다.

2. 페이지네이션 루프

GitHub 은 커밋을 한 번에 다 주지 않는다.

GET /repos/x/y/commits?per_page=100&page=1   → 100개
GET /repos/x/y/commits?per_page=100&page=2   → 100개
GET /repos/x/y/commits?per_page=100&page=3   →  37개   ← 100 미만 = 마지막

전부 가져오려면 page 를 올리며 반복해야 한다. 규약은 GitHub REST 페이지네이션 문서에 있다. 

var page = 1
val all = mutableListOf<CommitInsertDto>()
while (true) {
    val batch = getPage(page)
    all += batch
    if (batch.size < 100) break   // ← 종료 조건
    page++
}

종료 조건이 이 루프의 전부다. 틀리는 방식이 둘인데, 위험한 쪽은 조용한 쪽이다.

틀린 방식증상알아챌 수 있나
영영 안 멈춤무한 루프. rate limit 소진즉시 안다
너무 일찍 멈춤커밋이 조용히 누락아무도 모른다
이 저장소의 GithubClient 는 루프가 아예 없다. page=1 만 받고 끝난다 — 두 번째 칸의 극단이다. 커밋이 30건을 넘는 순간부터 조용히 사라지는데 예외도 로그도 없었다.

3. 루프를 포트의 어느 쪽에 둘 것인가

A — 포트 아래 (루프가 어댑터 안)

CommitService ──▶ GithubClientPort.fetchCommits(id, repo)
                       ├── GithubClient       ⟳ 루프
                       └── MockGithubClient     (루프 없음)

Mock 이 포트를 구현하므로, Mock 을 끼우면 루프를 통째로 건너뛴다. 종료 조건을 > 로 뒤집어 써도 테스트는 전부 초록불이다.

B — 포트 위 (루프가 서비스 안)

CommitService ⟳ ──▶ GithubClientPort.fetchCommits(id, repo, page)
                       ├── GithubClient         (한 페이지)
                       └── MockGithubClient     (한 페이지 — 흉내 가능)

루프가 검증된다. 대신 CommitService 가 "GitHub 은 100건씩 준다"를 알게 된다. 격리하려고 만든 포트에 GitHub 의 사정이 샌다.

C — 포트 아래 + 가짜 HTTP (경계를 소켓으로 내림)

CommitService ──▶ GithubClientPort
                       └── GithubClient ⟳ ──▶ MockRestServiceServer

루프도 검증되고 CommitService 는 여전히 아무것도 모른다. 대가는 GithubClient 를 테스트 가능하게 만드는 배선 — RestClient.Builder 를 주입받도록 바꾸는 것뿐이다.

루프 위치서비스가 GitHub 을 아는가루프를 검증하는 더블
A어댑터모른다없다
B서비스안다MockGithubClient
C어댑터모른다MockRestServiceServer

A 는 격리를 얻고 검증을 잃는다. B 는 검증을 얻고 격리를 잃는다. C 는 테스트 경계를 한 칸 아래로 내려 둘 다 가진다.

정직하게 남길 단서. MockRestServiceServer.bindTo(RestClient.Builder) 는 Spring Framework 6.1 부터 있고 이 프로젝트는 7.0.6 이라 쓸 수 있다 — spring-test 가 이미 testRuntimeClasspath 에 있어 의존성도 안 는다. 다만 Spring 공식 레퍼런스는 전송 계층까지 보려면 mock web server(WireMock 등)를 권한다. 여기서 C 를 고르는 건 그게 Spring 의 권장안이라서가 아니라, 검증 대상이 전송 계층이 아니라 루프 종료 조건이고 WireMock 은 의존성이 늘기 때문이다.

4. 확인

A 안(루프가 어댑터 안, Mock 은 포트 구현)에서 종료 조건을 반대로 쓰면?

Mock 이 포트를 구현하므로 루프 코드는 테스트 중 한 번도 실행되지 않는다. AGENTS.md 의 규칙 — "지웠을 때 아무 테스트도 안 깨지는 코드는 검증되고 있지 않은 것" — 에 정확히 걸린다.

C 안이 A 안에 비해 실제로 추가로 요구하는 것은?

GithubClient 가 지금은 생성자에서 RestClient 를 직접 만든다. RestClient.Builder 를 받도록 바꿔야 테스트가 거기 끼어들 수 있다. 의존성은 안 늘고(spring-test 는 이미 있다), 포트도 그대로다.

이 레슨의 일반 규칙

포트를 그릴 때 물을 것: "이 선 아래에 로직이 얼마나 있는가?" 선 아래가 얇은 번역층이면 A 로 충분하다. 선 아래에 판단이 있으면 — 루프, 재시도, 조건 분기 — 그 판단은 포트 더블로는 영영 검증되지 않는다. 그때 선택지는 판단을 선 위로 올리거나(B), 선을 하나 더 아래에 긋는 것(C)뿐이다.

먼저 읽을 것

Martin Fowler, Mocks Aren't Stubs — 테스트 더블의 종류와, 더블을 어디에 끼우느냐가 무엇을 검증하는지 바꾼다는 이 레슨의 주제를 가장 정확하게 다룬 글이다.
