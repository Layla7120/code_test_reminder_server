# ADR-0003: GitHub 커밋을 전체 이력으로 수집한다

**날짜** 2026-08-21 · **상태** 승인됨 · **관련** [0001](0001-사용자-삭제를-물리-삭제로-단일화한다.md), [0004](0004-페이지네이션-루프를-포트-아래-두고-http-를-가짜로-만든다.md)

## 맥락

`GithubClient.fetchCommits` 는 `/repos/{owner}/{repo}/commits` 를 **한 번** 호출한다.
`per_page` 도 `page` 도 없다. GitHub 기본값은 **30건**이다.

즉 커밋이 30건을 넘는 순간부터 **조용히 누락된다.** 예외도 로그도 없고,
누락됐다는 사실을 알 방법이 없다. 이 상한이 있다는 것 자체가 인지되지 않고 있었다.

이 사실이 다른 문서 두 곳을 거짓으로 만들고 있었다 —
구 docs/삭제-명세.md 와 `UserService` 주석의 *"GitHub 이 원본이다. 재가입 시 점수를
여기서 복구한다."* 최신 30건 범위에서만 참이었다.

## 결정

`?per_page=100&page=N` 을 **빈 응답이 올 때까지** 반복해 전체 이력을 수집한다.
페이지 수 상한을 두지 않는다.

## 검토하고 버린 것

**증분 수집 (`?since=` 로 마지막 수집 이후만).**
버린 이유 둘.

① **이 저장소가 이미 두 번 내린 판단에 역행한다.** 증분은 "마지막 수집 시각"이라는
상태를 들고 있어야 하고, 그 값이 한 번 틀리면 커밋이 영구히 누락된다. 랭킹 점수를
증분(`+= n`)에서 절대값(`COUNT(*)`)으로 바꾼 것이 정확히 같은 문제였다 —
`docs/기록.md` ② 참고.

② **[ADR-0001](0001-사용자-삭제를-물리-삭제로-단일화한다.md) 을 못 받쳐준다.**
물리 삭제 후 재가입하면 `since` 가 없어 다시 처음부터인데, 그게 지금의 30건 문제다.

**상한을 둔 전체 수집 (예: 최대 20페이지).**
버린 이유: **상한은 조용한 절단이고, 그게 지금 증상 그 자체다.** 30건 상한이 있는 줄도
몰랐던 상태에서 2,000건 상한을 새로 만드는 일이 된다.

## 결과

- **[ADR-0001](0001-사용자-삭제를-물리-삭제로-단일화한다.md) 의 전제가 실제로 성립한다.**
  *"GitHub 이 원본이다"* 가 지키지 못하는 약속에서 진짜 약속이 된다.
  재가입 시 커밋과 점수가 완전히 복원된다. 두 결정은 따로 보이지만 한 몸이다.
- `user_monthly_score` 의 절대값 재계산이 비로소 **전체에 대한 절대값**이 된다.
  지금은 "최신 30건에 대한 절대값"이라 이름값을 못 했다.
- **잃는 것**: `POST /commits` 응답 시간. 커밋 2,000개면 GitHub 호출 20회다.
  인증 시 rate limit 은 5,000/시간이라 여유가 있지만 **첫 수집은 수 초 걸린다.**
  느려서 문제가 되면 답은 **절단이 아니라 비동기화**이고, 그때 측정하고 결정한다.
  먼저 만들지 않는다.
- **아직 안 정한 것**: 3페이지째에서 GitHub 이 500 을 내면 부분 저장인가 전체 롤백인가.
  현재 구조상 트랜잭션이 통째로 롤백되므로 **아무 일도 일어나지 않는다**(재시도하면 됨).
  이 동작이 맞는지는 테스트로 고정하되, 부분 저장으로 바꿀 근거는 아직 없다.
