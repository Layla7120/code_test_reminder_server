# ADR-0006: member_counter 대사(reconciliation)를 두지 않는다

**날짜** 2026-08-21 · **상태** 승인됨(미구현) · **관련** [0002](0002-cascade-는-파생값의-원천이-아닐-때만-건다.md), `docs/삭제-명세.md` §6-4

## 맥락

`groups.member_counter` 는 `participate` 행 개수의 파생값이다.
`docs/삭제-명세.md` §5 가 *"`member_counter` == `participate` 실제 개수"* 를
**대사 없음**으로 표시해뒀고, §6-4 가 이를 미결정으로 남겨뒀다.

`PLAN-db-foundation.md` §1 의 4문 테스트에서도 이 열의 ④번(드리프트 감지·복구 수단)만
낙제로 남아 있었다 — 다른 두 사본(Redis ZSET, `user_monthly_score`)은 사본을 줄여서 해소됐다.

## 결정

**대사 잡을 만들지 않는다.** CHECK 제약(`0 <= member_counter <= member_max_count`)만
`PLAN-db-foundation.md` Phase 5 에서 걸고, *"실제 개수와 같은가"* 는 테스트로만 지킨다.

## 검토하고 버린 것

**주기적 대사 배치 (COUNT 와 비교해 로그·교정).**
버린 이유: **이 저장소가 이미 한 번 물린 패턴이다.** 랭킹 자가 치유 스케줄러가
정확히 *"파생값이 어긋나니 주기적으로 고치자"* 였고, ZADD GT 와 맞물려
**오히려 오염을 영구화**했다(`docs/기록.md` ②). 파생값 드리프트는 배치로 덮는 게 아니라
쓰기 경로를 하나로 줄여 없애는 것이 이 저장소의 확립된 방식이고,
`member_counter` 는 이미 원자적 조건부 `UPDATE` 하나가 유일한 쓰기 경로다.

**대사 쿼리만 만들고 자동 실행은 안 함.**
버린 이유: 아무도 안 돌리는 스크립트가 된다.

## 현업에서는 만드는가 — 조건이 있다

만든다. 단 **원천과 사본이 다른 트랜잭션 경계에 있을 때**다 —
검색 인덱스 재색인, 캐시, 데이터 웨어하우스, 다른 서비스의 DB, 결제 원장 대 은행 정산.
거기서는 원자적으로 같이 커밋할 방법이 **없으므로** 어긋남이 필연이고 감지 수단이 필수가 된다.

`member_counter` 는 반대다. 사본이 원천과 **같은 트랜잭션·같은 DB** 안에 있고
쓰기 경로가 원자적 조건부 `UPDATE` 하나다. 어긋나려면 코드에 버그가 있어야 하는데,
그건 대사가 아니라 테스트가 잡을 문제다.

그리고 현업에서도 두 형태를 구분한다 — **경보만 하는 대사**(불일치를 알리고 사람이 판단)와
**자동 교정 대사**. 후자가 위험한 쪽이고, 이 저장소가 정확히 거기서 물렸다.

> **미해결로 남기는 것**: 위 판단("원천과 사본이 다른 트랜잭션 경계에 있을 때")의
> 근거가 될 신뢰할 만한 1차 자료를 아직 못 찾았다. `docs/learning/RESOURCES.md` 의
> Gaps 에 적어뒀다. 경험칙이지 인용이 아니다.

## 결과

- `PLAN-db-foundation.md` §1 4문 테스트의 마지막 낙제 칸이 **"채우지 않기로 결정"** 으로 닫힌다.
- **잃는 것**: `member_counter` 가 실제와 어긋나도 감지할 수단이 없다.
  이 결정은 그 위험을 **없앤 게 아니라 받아들인 것**이다.
  받아들일 수 있는 근거는 쓰기 경로가 하나라는 것뿐이고,
  **경로가 늘어나는 순간 이 ADR 을 다시 검토해야 한다.**
- [ADR-0002](0002-cascade-는-파생값의-원천이-아닐-때만-건다.md) 가 `participate.user_id` 를
  RESTRICT 로 둔 이유가 이것이다 — CASCADE 는 쓰기 경로를 하나 더 만든다.

## 어떻게 지켜지나

- `GroupJoinConcurrencyTest`, `GroupLeaveTest`, `GroupMemberApiTest` — 기존 테스트가
  카운터 정확성을 고정한다
- `SchemaContractTest` — `participate.user_id` 가 CASCADE 가 아님을 확인
  (경로가 늘어나는 것을 DDL 수준에서 막는다)
- Phase 5 의 CHECK 제약 — **범위**는 DB 가 막지만 *"실제 개수와 같은가"* 는 못 막는다.
  이 구별을 여기 적어두는 게 이 ADR 의 목적 중 하나다.
