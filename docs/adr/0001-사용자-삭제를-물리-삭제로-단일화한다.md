# ADR-0001: 사용자 삭제를 물리 삭제로 단일화한다

**날짜** 2026-08-21 · **상태** 승인됨 · **관련** [0002](0002-cascade-는-파생값의-원천이-아닐-때만-건다.md), [0003](0003-github-커밋을-전체-이력으로-수집한다.md)

## 맥락

`9b3b90e` 이후 탈퇴는 소프트 삭제였다. `users.active = false` 로 두고 행은 남기며,
같은 `githubId` 로 다시 로그인하면 재활성화하고 `commits` 에서 점수를 복구했다.

구 docs/삭제-명세.md §6 이 "아직 정하지 않은 것" 네 개를 명시적으로 열어두고 있었다 —
보관 기간(무기한이 **의도가 아니라 방치의 결과**), 물리 삭제 경로 부재,
비활성 유저의 커밋 취급, 대사 부재.

결정 시점에 세 가지 사실이 확인됐다.

**① 실사용자가 없다.** 배포 설정이 저장소에 없고(`.github/workflows/` 에 `test.yml` 뿐),
`docker-compose.yml` 은 로컬 MySQL 하나다. 파괴적 변경이 지금은 싸다.

**② 소프트 삭제의 근거 문장이 사실이 아니었다.** `UserService` 주석과 명세서가
*"GitHub 이 원본이다. 재가입 시 점수를 여기서 복구한다"* 고 적었는데,
`GithubClient.fetchCommits` 는 `/repos/{owner}/{repo}/commits` 를 **페이지네이션 없이
한 번** 호출한다(`per_page`·`page` 없음 → 기본 30건). 복구는 **최신 30건 범위에서만** 참이었다.

**③ 소프트 삭제가 앱 코드로만 지키는 불변조건 두 개를 만들고 있었다.**
구 docs/삭제-명세.md §5 가 그 둘에 ⚠️ 를 달고 *"이 명세의 약한 고리"* 라고 적어뒀다 —
비활성 유저는 `user_monthly_score` 행이 없다, `participate` 행이 없다. DB 가 막아주지 않는다.

## 결정

**탈퇴 = 행 삭제.** `users.active` 컬럼과 그에 딸린 코드를 전부 제거한다.

| | 이전 | 이후 |
|---|---|---|
| 탈퇴 | `active = false`, 행 유지 | **행 삭제** |
| 재가입 | 같은 `user_id` 로 재활성화 + 점수 복구 | **완전한 신규 유저.** 새 `user_id` |
| `nickname` · `github_id` | 계속 점유 | **반납.** 남이 쓸 수 있다 |
| `GET /users?userId=` (탈퇴 후) | 200, `active: false` | **404** |

그룹 정리는 그대로다 — 물리 삭제 전에 `GroupService.leaveGroup` 을 모든 참여에 대해
돌린다. 오너 승계와 빈 그룹 삭제가 거기 있다.

## 검토하고 버린 것

**소프트 삭제 유지 + 물리 삭제 경로 없음 (현상 유지).**
버린 이유: 위 ③ 이 남는다. 앱 코드로만 지키는 불변조건 두 개가 계속 "약한 고리"로 남고,
새 쓰기 경로가 생기면 조용히 깨진다.

**소프트 삭제 후 N개월 뒤 물리 삭제 (산업 표준).**
버린 이유: **탈퇴 시각을 담을 컬럼이 없다.** `users` 에 `created_at`/`updated_at` 은 있지만
`updated_at` 은 프로필 수정으로도 바뀌어 대용이 안 된다. `deactivated_at` 컬럼 + 만료 배치 +
배치 테스트가 새로 필요하다. **실사용자가 없는데 보관 기간 만료 로직을 만드는 건
정확히 이 저장소가 반복해 물린 "필요 없는 복잡도"다.**

## 결과

**사라지는 것** — 이게 이 결정의 목적이다:

| 사라지는 것 | 있던 곳 |
|---|---|
| `users.active` 컬럼과 이를 읽는 분기 2곳 | `UserService.loginOrCreate`, `CommitService.fetchAndSaveCommits` 의 `if (user.active)` |
| 재활성화·점수 백필 경로 | `User.reactivate()`, `UserService.restoreScores`, `backfillFromCommits` |
| 앱 코드로만 지키던 불변조건 2개 | 구 docs/삭제-명세.md §5 — 유저 행이 없으면 **자명하게** 참 |
| "행이 있다 = 랭킹 포함" 규칙의 설명 부담 | README · 명세서 · 주석 3곳에 반복 서술 중이었다 |
| 좀비 계정 개념, 재가입 복구 범위 논쟁 | 명세서 §3 표 전체 |

**잃는 것 — 정직하게 적는다:**

- 재가입 시 `user_id`·`commits`·`history` 가 안 돌아온다.
  단 `commits` 는 [ADR-0003](0003-github-커밋을-전체-이력으로-수집한다.md) 으로
  **전체 복원되므로 실질 손실이 아니다.** 두 결정은 한 몸이다.
- `nickname`·`github_id` 를 남이 선점할 수 있다. 실사용자가 없어 지금이 유일하게 싼 시점이다.
- `history` 는 복원되지 않는다. 사용자가 직접 입력한 값이라 외부 원천이 없다.
  **이 결정으로 영구 손실이 생기는 유일한 데이터다.**
- `DELETE /users/delete` 후 `GET /users` 가 404 가 된다. API 계약 변경이므로
  `AGENTS.md` 규칙에 따라 HTTP 계층 테스트를 함께 낸다.

## 어떻게 지켜지나

- `SchemaContractTest` — `users` 에 `active` 컬럼이 없음을 `information_schema` 로 확인
- 죽은 코드 스크립트 — `active` 를 참조하는 잔재가 남으면 실패
- `UserLifecycleApiTest` (개정) — 탈퇴 후 `GET /users` 가 404, 닉네임 재사용 가능
