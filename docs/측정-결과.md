# 랭킹 A/B 측정 결과

> 바꾼 변수는 **하나뿐**: `ranking.redis.enabled`
> 코드·DB·시드 데이터·VU 수·지속 시간·엔드포인트 구성·커넥션 풀은 전부 고정.
>
> 실행 방법과 설계 근거 → [`bench/README.md`](../bench/README.md)
> 원본 결과 → [`bench/results/`](../bench/results/)

## 측정 조건

| 항목 | 값 |
|---|---|
| 도구 | k6 v2.1.0, `constant-vus` VU 30, 60초 |
| 엔드포인트 | `GET /rank` 70% + `GET /rank/users?userId=N` 30% |
| 규모 | 유저 1만 / 5만 / 10만 (유저당 커밋 1~40건) |
| DB | MySQL 8.0, HikariCP `maximum-pool-size=20`, `connection-timeout=3000ms` |
| 팔 A (`redis`) | Redis ZSET `ZREVRANGE` + score→denseRank HASH `HGET` |
| 팔 B (`db`) | MySQL `DENSE_RANK()` 윈도우 함수 — 전체 유저 정렬 |

`db` 팔은 벤치마크용 별도 구현이 아니라 **운영에 이미 있는 Redis 장애 폴백 경로**다
(`RankService.getTop30FromDb()`). 그래서 이 측정은 "Redis가 죽으면 어떻게 되나"도 함께 답한다.

## 결과 — 처리량과 실패율

**이게 핵심 지표다.** (아래에서 설명하듯 db 팔의 지연 수치는 규모가 커지면 지표로서 무의미해진다)

| 유저 수 | 팔 | 처리량 | 실패율 | 60초간 처리 건수 |
|---|---|---|---|---|
| 1만 | `redis` | **7,873 req/s** | 0% | 472,786 |
| 1만 | `db` | 10.0 req/s | 0% | 619 |
| 5만 | `redis` | **5,481 req/s** | 0% | 329,017 |
| 5만 | `db` | 3.5 req/s | **64.6%** | 226 |
| 10만 | `redis` | **9,325 req/s** | 0% | 559,532 |
| 10만 | `db` | 3.3 req/s | **86.2%** | 217 |

### 기울기가 말하는 것

**`redis` 팔은 유저가 10배 늘어도 평평하다.** 처리량 5,481~9,325 req/s 사이를 오가는데,
이 편차는 규모 때문이 아니라 **실행 간 노이즈**다(각 조건 1회씩만 측정 — 아래 한계 참조).
10만 규모가 5만보다 빠르게 나온 게 그 증거다. ZSET 조회는 `O(log N + 30)`이라
유저 수와 사실상 무관하다는 설계 의도가 그대로 나타났다.

**`db` 팔은 느려지는 게 아니라 무너진다.**
1만에서 이미 10 req/s로 바닥이고, 5만부터는 요청의 **3분의 2가 실패**한다.
10만에서는 **10건 중 9건이 실패**한다.

## db 팔의 지연 수치를 그대로 쓰지 않는 이유

k6가 뽑은 p95는 이렇다.

| 유저 수 | `db` top30 p95 | 그런데 |
|---|---|---|
| 1만 | 4.43초 | 실패 0% → **이 값은 신뢰할 수 있다** |
| 5만 | 22.93초 | 실패 64.6% |
| 10만 | 43.79초 | 실패 86.2% |

5만·10만의 값은 **"느린 성공"과 "3초 만에 빠르게 실패한 요청"이 섞인 혼합값**이다.
`min=3s`, `med=3.01s`가 그 증거 — 이건 쿼리 시간이 아니라 HikariCP의
`connection-timeout=3000ms`가 그대로 찍힌 것이다.

서버 로그에서 확인한 실제 원인:

```
HikariPool-1 - Connection is not available, request timed out after 3005ms
             (total=20, active=20, idle=0, waiting=9)
SQLTransientConnectionException  ... 187건 (10만 db 팔)
```

`DENSE_RANK()` 한 방이 수 초씩 커넥션을 붙잡으니 20개 풀이 즉시 포화되고,
뒤에 온 요청은 쿼리를 시작해보지도 못하고 3초 뒤 5xx로 떨어진다.

> **평균값의 함정 하나** — `db` 팔 평균이 5만에서 9.52초, 10만에서 8.71초로 **줄어든다.**
> 10만이 더 빨라진 게 아니라, 실패가 늘어서 3초짜리 빠른 실패가 평균을 끌어내린 것이다.
> 실패율을 같이 보지 않으면 정반대로 해석하게 되는 지점이다.

## "그건 커넥션 풀 크기 문제 아닌가?" — 보조 측정

정당한 반론이라 따로 쟀다. **동시성 1, 순차 요청** — 풀 대기가 발생할 수 없는 조건이다.
(워밍업 5회 후 10회 측정, 중앙값)

| 유저 수 | 팔 | `GET /rank` | `GET /rank/users` |
|---|---|---|---|
| 1만 | `redis` | **3.1 ms** | **2.3 ms** |
| 1만 | `db` | 1,546.6 ms | 72.4 ms |
| 5만 | `redis` | **3.7 ms** | **3.5 ms** |
| 5만 | `db` | 3,713.2 ms | 530.5 ms |
| 10만 | `redis` | **4.0 ms** | **3.5 ms** |
| 10만 | `db` | 8,005.9 ms | 1,209.2 ms |

### 답: 풀 문제가 아니다

**동시성 1이라 커넥션 대기가 발생할 수 없는데도** DB 경로의 Top30은
유저 1만에서 이미 1.5초, 10만에서 8초다. 쿼리 자체가 비싼 것이다.

풀 포화는 원인이 아니라 **결과**다 — 쿼리 하나가 수 초씩 커넥션을 붙잡으니
20개짜리 풀이 버티지 못한 것이지, 풀이 작아서 쿼리가 느려진 게 아니다.

### 기울기 — 유저를 10배(1만→10만) 늘렸을 때

| | `GET /rank` | `GET /rank/users` |
|---|---|---|
| `redis` | 3.1 → 4.0 ms (**1.3배**) | 2.3 → 3.5 ms (**1.5배**) |
| `db` | 1,546.6 → 8,005.9 ms (**5.2배**) | 72.4 → 1,209.2 ms (**16.7배**) |

**두 경로의 격차 자체가 규모와 함께 벌어진다.** 이게 기울기가 다르다는 것의 가장 직접적인 표현이다.

| 유저 수 | `GET /rank` db÷redis | `GET /rank/users` db÷redis |
|---|---|---|
| 1만 | 499배 | 31배 |
| 5만 | 1,004배 | 152배 |
| 10만 | **2,001배** | **345배** |

Redis 경로가 평평한 것은 `ZREVRANGE 0 29`가 `O(log N + 30)`이고,
개인 순위는 score→denseRank HASH를 `HGET` 한 번으로 끝내기 때문이다 — 둘 다 유저 수와 사실상 무관하다.
DB 경로는 `DENSE_RANK()`가 매 요청마다 **전체 유저를 정렬**하므로 유저 수를 그대로 떠안는다.

## 한계 (알고 있는 것)

- **부하 측정(VU 30)은 각 조건 1회씩만 했다.** `redis` 팔의 처리량이 5만(5,481 req/s)보다
  10만(9,325 req/s)에서 높게 나온 역전이 그 한계를 보여준다. 기울기의 방향을 보기엔
  충분하지만, 같은 팔 안의 처리량 차이는 의미를 두면 안 된다.
  (보조 측정은 워밍업 5회 후 10회 측정의 중앙값이라 이 문제가 덜하다)
- **로컬 단일 머신**에서 앱·MySQL·Redis·k6가 자원을 공유한다. 절대값은 환경에 종속적이다.
  이 측정의 목적은 절대 성능이 아니라 **두 경로의 기울기 비교**다.
- 커넥션 풀 20개는 두 팔에 동일하게 적용된 **고정 조건**이지 `db` 팔만의 핸디캡이 아니다.
  같은 풀로 `redis` 팔은 9,325 req/s를 0% 실패로 처리했다.

## 이 측정이 답하는 질문 두 개

**1. "왜 랭킹을 Redis로 옮겼나요?"**

유저 10만 기준으로 DB 경로는 초당 3.3건에서 86% 실패한다. Redis 경로는 같은 조건에서
9,325건을 0% 실패로 처리한다. 그리고 규모를 10배 키워도 Redis 쪽은 평평하다.

**2. "Redis가 죽으면요?"**

`db` 팔이 곧 그 답이다. 폴백은 **동작한다** — 하지만 견디는 범위가 좁다.

| 규모 | 폴백 상태 |
|---|---|
| 유저 1만 | 견딤. 10 req/s, 실패 0%. 다만 Top30 응답이 초 단위(p95 4.4초) |
| 유저 5만 | 요청의 **64.6% 실패** |
| 유저 10만 | 요청의 **86.2% 실패** |

즉 이 폴백은 "성능 저하를 감수하고 가용성을 지키는" 장치가 아니라
**"짧은 장애를 버티는" 장치**다. Redis 장애가 길어지면 폴백만으로는 못 버틴다.

**지금 답할 수 없는 것도 분명히 해둔다** — 장애가 길어질 때의 대책(랭킹 응답을
degrade해서 내보내기, 요청 차단, Redis 이중화)은 **이 프로젝트 범위에 넣지 않았다.**
"폴백이 있으니 괜찮다"가 아니라 "폴백은 1만 규모까지만 유효하고 그 이상은 대책이 없다"가
정확한 현재 상태다.
