## 먼저: 1차 측정은 공정하지 않았다

처음에는 **"DB 조건이 2,001배 느리다"** 고 적었다. 그 숫자는 버렸다.

그때의 `findTop30Rank`는 **아무도 읽지 않는 컬럼 3개**를 함께 뽑고 있었다.

| 컬럼 | 코드베이스 내 호출 횟수 |
|---|---|
| `githubId` | 0회 |
| `nickname` | 0회 |
| `previousMonthCount` | 0회 |

안 쓰는 VARCHAR 둘이 `GROUP BY` 키를 넓혀 10만 행을 넓은 정렬 키로 그룹핑하게 만들었고,
안 쓰는 지난달 집계 때문에 조인 범위가 1개월 → 2개월로 늘어나 있었다.
**Redis를 군살 붙은 쿼리와 비교한 셈이다.**

쿼리를 응답에 실제로 쓰이는 컬럼만 조회하도록 고치고(커밋 `6b6674d`) 전부 다시 쟀다.

| | 1차 (군살 있음) | 2차 (수정 후) |
|---|---|---|
| `GET /rank` DB, 10만, 동시성 1 | 8,005.9 ms | **464.9 ms** |
| Redis 대비 배수 | 2,001배 | **179배** |
| 10만 부하 테스트 실패율 (DB) | 86.2% | **2.84%** |

여전히 결정적이지만 **서사가 달라졌다** — DB 경로는 "무너지는" 게 아니라 "느려지는" 것이었다.

> 이 정정을 지우지 않고 남겨두는 이유:
> **측정 대상이 최선의 구현인지 먼저 확인하지 않으면 허수아비를 이기게 된다.**
> 결과 자체보다 이 점이 더 오래 쓸모 있다.
>
> 그리고 `DENSE_RANK()` 는 범인이 아니었다. 유저 10만 기준 실측(MySQL 직접 호출):
>
> | | 시간 |
> |---|---|
> | 안 쓰는 컬럼 제거, **DENSE_RANK 유지** | 531 ms |
> | 거기서 DENSE_RANK 까지 제거 | 522 ms |
>
> **윈도우 함수 비용은 9ms — 전체의 2%.** 빼도 의미가 없다.

## 측정 조건

| 항목 | 값 |
|---|---|
| 도구 | k6 v2.1.0, `constant-vus` VU 30, 60초 |
| 엔드포인트 | `GET /rank` 70% + `GET /rank/users?userId=N` 30% |
| 규모 | 유저 1만 / 5만 / 10만 (유저당 커밋 1~40건) |
| DB | MySQL 8.0, HikariCP `maximum-pool-size=20`, `connection-timeout=3000ms` |
| 조건 A (`redis`) | Redis ZSET `ZREVRANGE` + score→denseRank HASH `HGET` |
| 조건 B (`db`) | MySQL `DENSE_RANK()` — 전체 유저 집계 후 정렬 |

> **"조건(arm)"** 은 A/B 테스트에서 비교하는 각각의 설정을 말한다.

`db` 조건은 벤치마크용 별도 구현이 아니라 **운영에 이미 있는 Redis 장애 폴백 경로**다
(`RankService.getTop30FromDb()`). 그래서 이 측정 하나가 "Redis가 죽으면 어떻게 되나"도 함께 답한다.

## 결과 1 — 동시성 1 (순수 쿼리 비용)

경합이 없으므로 커넥션 풀 대기가 발생할 수 없다. **쿼리 자체의 비용만 본다.**
(워밍업 5회 후 10회 측정, 중앙값)

| 유저 수 | 조건 | `GET /rank` | `GET /rank/users` |
|---|---|---|---|
| 1만 | `redis` | **2.4 ms** | **2.9 ms** |
| 1만 | `db` | 43.2 ms | 58.2 ms |
| 5만 | `redis` | **2.6 ms** | **3.0 ms** |
| 5만 | `db` | 202.7 ms | 275.0 ms |
| 10만 | `redis` | **2.6 ms** | **3.0 ms** |
| 10만 | `db` | 464.9 ms | 608.4 ms |

### 기울기 — 유저를 10배(1만→10만) 늘렸을 때

| | `GET /rank` | `GET /rank/users` |
|---|---|---|
| `redis` | 2.4 → 2.6 ms (**1.1배**) | 2.9 → 3.0 ms (**1.03배**) |
| `db` | 43.2 → 464.9 ms (**10.8배**) | 58.2 → 608.4 ms (**10.5배**) |

**Redis는 평평하고, DB는 유저 수에 거의 정비례한다.**

격차 자체가 규모와 함께 벌어진다:

| 유저 수 | `GET /rank` db÷redis | `GET /rank/users` db÷redis |
|---|---|---|
| 1만 | 18배 | 20배 |
| 5만 | 78배 | 92배 |
| 10만 | **179배** | **203배** |

Redis가 평평한 이유는 `ZREVRANGE 0 29`가 `O(log N + 30)`이고,
개인 순위는 score→denseRank HASH를 `HGET` 한 번으로 끝내기 때문이다 — 둘 다 유저 수와 사실상 무관하다.
DB는 매 요청마다 **이번 달 커밋 전체를 집계**해야 하므로 데이터 양을 그대로 떠안는다.

## 결과 2 — 동시 30명 (부하)

| 유저 수 | 조건 | 처리량 | 실패율 | `GET /rank` p95 |
|---|---|---|---|---|
| 1만 | `redis` | **23,865 req/s** | 0% | **1.97 ms** |
| 1만 | `db` | 102 req/s | 0% | 393.82 ms |
| 5만 | `redis` | **17,863 req/s** | 0% | **2.57 ms** |
| 5만 | `db` | 18.6 req/s | 0% | 1.84 초 |
| 10만 | `redis` | **13,692 req/s** | 0% | **3.57 ms** |
| 10만 | `db` | 6.1 req/s | 2.84% | 9.36 초 |

**처리량 배수: 234배 → 961배 → 2,246배.**
동시성이 붙으면 격차가 더 벌어진다. 커넥션 풀(20개)이 병목으로 추가되기 때문이다.

10만 `db` 조건의 실패 2.84%는 HikariCP `connection-timeout=3000ms` 초과다.
1차 측정(86.2%)에 비하면 미미하지만, **여기서부터 한계가 보이기 시작한다**는 신호다.

## 한계 (알고 있는 것)

- **각 조건 1회씩만 측정했다.** `redis` 조건의 처리량이 규모가 커질수록 낮아지는 것처럼
  보이지만(23,865 → 17,863 → 13,692), 지연은 오히려 평평하다(1.97 → 2.57 → 3.57 ms).
  처리량 차이는 규모 효과라기보다 **실행 간 노이즈와 머신 상태**로 보는 게 맞다.
  방향을 보기엔 충분하지만 같은 조건 안의 수치 차이에 의미를 두면 안 된다.
- **로컬 단일 머신**에서 앱·MySQL·Redis·k6가 자원을 공유한다. 절대값은 환경 종속적이다.
  목적은 절대 성능이 아니라 **두 경로의 기울기 비교**다.
- 커넥션 풀 20개는 두 조건에 **동일하게 적용된 고정 조건**이지 `db` 조건만의 핸디캡이 아니다.
  같은 풀로 `redis` 조건은 13,692 req/s를 0% 실패로 처리했다.
- `findUserRank`는 손대지 않았다. 그 쿼리는 안 쓰는 컬럼이 없고,
  `currentMonthCount`가 `DENSE_RANK`의 정렬 기준이라 이미 계산되어 있어 뺄 게 없다.
  **전역 순위를 원본 데이터에서 매기려면 전체 집계가 불가피하다** — 쿼리 튜닝으로 없앨 수 없는 비용이고,
  그래서 오히려 사전 계산(Redis)의 근거가 된다.

## 이 측정이 답하는 질문 두 개

### 1. "왜 랭킹을 Redis로 옮겼나요?"

유저 10만 기준, 동시 30명일 때 DB 경로는 초당 6건을 처리하고 p95가 9.36초다.
Redis 경로는 같은 조건에서 13,692건을 0% 실패로 처리하고 p95가 3.57ms다.

더 중요한 건 **기울기**다. 유저를 10배 늘렸을 때 Redis는 1.1배 느려지는 데 그쳤고
DB는 10.8배 느려졌다 — 유저 수에 거의 정비례한다.

### 2. "Redis가 죽으면요?"

`db` 조건이 곧 그 답이다. 폴백은 **동작한다**. 다만 견디는 범위가 있다.

| 규모 | 폴백 상태 |
|---|---|
| 유저 1만 | 견딤. 102 req/s, 실패 0%, p95 394ms |
| 유저 5만 | 느리지만 버팀. 18.6 req/s, 실패 0%, p95 1.84초 |
| 유저 10만 | 한계. 6.1 req/s, 실패 2.84%, p95 9.36초 |

즉 이 폴백은 **"짧은 장애를 버티는" 장치**다. 1만 규모까지는 사용자가 느리다고 느끼는 정도지만,
10만에서는 실질적으로 서비스가 어렵다.

**지금 답할 수 없는 것도 분명히 해둔다** — 장애가 길어질 때의 대책(랭킹을 degrade해서 내보내기,
요청 차단, Redis 이중화)은 **이 프로젝트 범위에 넣지 않았다.**
"폴백이 있으니 괜찮다"가 아니라 **"폴백은 1만 규모까지만 여유가 있고 그 이상은 대책이 없다"** 가
정확한 현재 상태다.
