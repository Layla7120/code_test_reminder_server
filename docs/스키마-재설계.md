# 스키마 재설계 — 직접 짜고 대조하기

> **사용법**: 아래 1~3장만 보고 4장에 직접 설계하세요.
> `infra/init.sql`은 **다 짜고 나서** 여세요. 먼저 보면 같은 걸 다시 도출하게 됩니다.
>
> 다 짜시면 대조해 드립니다. 기준은 5장에 미리 공개해 뒀습니다.

---

## 1. 도메인 — 이 서비스가 하는 일

알고리즘 문제 풀이 독려 서비스 "코테독촉기".

- 유저는 자신의 **GitHub 저장소**를 등록한다. 그 저장소에는 백준 풀이 커밋이 쌓인다
- 커밋 메시지 형식: `[GOLD IV] Title: 두 수의 합, Time: 0ms, Memory: 2000KB -`
  - 여기서 **난이도**와 **문제 제목**을 파싱한다. 난이도는 BRONZE~RUBY + UNRATED
- 서버가 GitHub API로 커밋을 가져와 저장한다. 같은 커밋을 여러 번 가져와도 중복 저장되면 안 된다
- **이번 달 커밋 수**로 전체 랭킹을 매긴다 (동점자는 같은 등수 — DENSE_RANK)
- 유저는 **그룹**을 만들거나 참여한다. 그룹은 정원과 선택적 비밀번호가 있다
- 그룹 안에서 멤버들의 이번 달 / 지난달 커밋 수를 비교해 보여준다
- 별도로 **문제 풀이 기록(history)** 을 남긴다: 문제 번호와 걸린 시간

## 2. 실제 쿼리 목록 — 스키마를 결정하는 것은 이것입니다

코드에서 뽑은 전부입니다. **모든 쿼리가 인덱스를 타야 합니다.**

### 랭킹 (가장 뜨거운 경로)

| # | 쿼리 | 빈도 |
|---|------|------|
| R1 | 전체 유저 중 **이번 달 커밋 수 상위 30명** + 각자의 지난달 커밋 수 + DENSE_RANK | 매우 높음 |
| R2 | **특정 유저 1명**의 이번 달 순위 | 매우 높음 |
| R3 | (스케줄러, 매시간) **전체 유저의 이번 달 커밋 수 집계** — `GROUP BY user_id` | 시간당 1회, 전체 스캔 |

> R1·R2는 Redis로 오프로딩되어 있으나 **Redis 장애 시 DB 폴백**이 돌아야 합니다.
> R3는 Redis를 DB 기준으로 보정하는 근거라 항상 DB에서 돕니다.

### 커밋

| # | 쿼리 |
|---|------|
| C1 | 한 유저의 커밋 N건 **벌크 삽입, 이미 있는 건 건너뜀** |
| C2 | 한 유저의 **최근 7일** 중 커밋한 날짜 목록 |
| C3 | 한 유저의 **이번 달 + 지난달**, 날짜별 커밋 수 (잔디) |
| C4 | 한 유저의 **난이도별** 커밋 수 (전 기간) |

### 그룹

| # | 쿼리 |
|---|------|
| G1 | 유저가 속한 그룹 조회 |
| G2 | 그룹 멤버 전원의 **이번 달 / 지난달 커밋 수 + 그룹 내 순위** |
| G3 | 그룹 참여 — **정원이 안 찼을 때만** 참여 성공 (동시 요청에서 정확히 정원까지만) |
| G4 | 그룹 탈퇴 |
| G5 | 그룹명 **중복 확인** |
| G6 | 그룹명 **앞부분 일치 검색** (`LIKE 'abc%'`) |
| G7 | 소유자 확인 후 비밀번호 변경 |

### 유저 / 히스토리

| # | 쿼리 |
|---|------|
| U1 | 닉네임 중복 확인 |
| U2 | 닉네임 · 저장소명 수정 |
| U3 | 탈퇴 (현재는 소프트 삭제 — `active = false`) |
| H1 | 문제 풀이 기록 저장 / 조회 |

## 3. 직접 정해야 할 것 — 여기가 설계의 핵심입니다

정답을 드리지 않겠습니다. **각 항목에 "무엇을 골랐고 왜"를 4장에 적으세요.**
면접에서 물어보는 건 결과물이 아니라 이 선택의 근거입니다.

1. **유저는 그룹에 몇 개까지 속하는가?**
   1개면 DB가 막아야 하고, 여러 개면 조회 API가 목록을 반환해야 합니다.
   지금 코드는 스키마와 애플리케이션의 답이 서로 다릅니다.

2. **커밋의 유일성은 무엇으로 판정하는가?**
   GitHub sha는 저장소를 포크하면 서로 다른 유저에게 같은 값이 나옵니다.
   유일성 범위를 어디까지 잡을 것인가?

3. **탈퇴한 유저의 닉네임을 다른 사람이 쓸 수 있는가?**
   소프트 삭제와 UNIQUE 제약은 서로 부딪힙니다. 어느 쪽을 택할 것인가?

4. **`history`에 "언제"가 필요한가?**
   지금은 걸린 시간(`"01:23:45"` 문자열)만 있고 **푼 시각이 없습니다.**
   시각이 필요한가? `solve_time`의 타입은 무엇이어야 하는가?

5. **같은 문제를 여러 번 푼 것을 구분해야 하는가?**
   `commits`에는 문제 제목만 있고 **문제 번호가 없습니다**(`history`에는 있음).
   랭킹이 "푼 문제 수"인가 "커밋 수"인가에 따라 답이 달라집니다.

6. **난이도(`level`)를 어떻게 저장하는가?**
   지금은 검증 없는 문자열입니다. 알 수 없는 값이 들어와 `UNRATED`로 떨어뜨린 이력이 있습니다.
   (커밋 `55a4861`)

7. **정원 초과 · 카운터 음수를 DB가 막는가, 애플리케이션이 막는가?**
   지금은 애플리케이션만 막습니다. 코드 한 줄이 틀리면 데이터가 조용히 망가집니다.
   실제로 그런 결함이 있습니다.

8. **역정규화된 `member_counter`를 유지할 것인가?**
   유지/제거 각각의 대가를 적으세요. (이미 결론이 난 항목이지만 근거를 다시 쓰는 게 좋습니다)

### 제약 조건

- MySQL 8.0 (`CHECK` 제약, 윈도우 함수, 생성 컬럼 모두 사용 가능)
- 규모 가정: 유저 10만, 유저당 월 100커밋 → `commits` 연 1억 건
- 랭킹 R1·R2는 Redis가 처리하지만, **DB만으로도 응답 가능해야 함** (폴백)

## 4. 내 설계

> 여기에 직접 작성하세요. DDL이어도 되고, 표나 그림이어도 됩니다.

### 4-1. 테이블

> 초안(에이전트). N=7 반영. 수정하면서 다듬으면 됨.

```sql
CREATE TABLE users (
    user_id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    github_id       VARCHAR(100)  NOT NULL,
    nickname        VARCHAR(50)   NOT NULL,
    repository_name VARCHAR(200)  NOT NULL,
    deactivated_at  DATETIME(6)   NULL COMMENT '탈퇴 시각. NULL = 활성. 7일 후 하드 삭제 대상',
    created_at      DATETIME(6)   NOT NULL,
    updated_at      DATETIME(6),
    CONSTRAINT uk_users_github_id UNIQUE (github_id),
    CONSTRAINT uk_users_nickname  UNIQUE (nickname)
    -- active 컬럼 없음 → 4-3 #3
);

CREATE TABLE commits (
    commit_id   BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT        NOT NULL,
    commit_date DATETIME(6)   NOT NULL,
    commit_url  VARCHAR(500)  NOT NULL,
    title       VARCHAR(200)  NOT NULL,
    level       VARCHAR(20)   NOT NULL,  -- 세부 티어 또는 UNRATED (앱/백준허브 신뢰)
    sha         VARCHAR(40)   NOT NULL,
    CONSTRAINT uk_commits_user_sha UNIQUE (user_id, sha),
    CONSTRAINT fk_commits_user FOREIGN KEY (user_id)
        REFERENCES users(user_id) ON DELETE CASCADE
);

CREATE TABLE `groups` (
    group_id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    group_name       VARCHAR(100) NOT NULL,
    group_pw         VARCHAR(60),          -- nullable = 비번 없음. BCrypt 해시
    member_max_count INT          NOT NULL DEFAULT 5,
    member_counter   INT          NOT NULL DEFAULT 0,
    owner_id         BIGINT       NOT NULL, -- 승계 시 UPDATE 가능해야 함
    created_at       DATETIME(6)  NOT NULL,
    updated_at       DATETIME(6),
    CONSTRAINT uk_groups_name UNIQUE (group_name),
    CONSTRAINT chk_groups_max CHECK (member_max_count >= 1),
    CONSTRAINT chk_groups_counter CHECK (member_counter >= 0
                                     AND member_counter <= member_max_count),
    CONSTRAINT fk_groups_owner FOREIGN KEY (owner_id)
        REFERENCES users(user_id) ON DELETE RESTRICT
    -- member_counter 유지 + 원자적 조건부 UPDATE → 4-3 #7, #8
);

CREATE TABLE participate (
    participate_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    group_id       BIGINT      NOT NULL,
    user_id        BIGINT      NOT NULL,
    created_at     DATETIME(6) NOT NULL,  -- 승계 시 "최연장자" 판정
    updated_at     DATETIME(6),
    CONSTRAINT uk_participate_group_user UNIQUE (group_id, user_id),
    CONSTRAINT fk_participate_group FOREIGN KEY (group_id)
        REFERENCES `groups`(group_id) ON DELETE CASCADE,
    CONSTRAINT fk_participate_user FOREIGN KEY (user_id)
        REFERENCES users(user_id) ON DELETE CASCADE
    -- user_id 단독 UNIQUE 없음(다중 참여), 유저당 상한은 앱 → 4-3 #1
);

CREATE TABLE history (
    history_id  BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT       NOT NULL,
    problem_num VARCHAR(20)  NOT NULL,
    solve_time  INT          NOT NULL COMMENT '소요 초',
    solved_at   DATETIME(6)  NOT NULL COMMENT '푼 시각',
    CONSTRAINT chk_history_solve_time CHECK (solve_time >= 0),
    CONSTRAINT fk_history_user FOREIGN KEY (user_id)
        REFERENCES users(user_id) ON DELETE CASCADE
    -- append-only, PB는 MIN(solve_time) → 4-3 #5
);
```

**하드 삭제 배치(요약):** `deactivated_at <= now() - INTERVAL 7 DAY` 유저에 대해
그룹은 앱에서 승계/해산 후 → user DELETE (commits/history/participate는 CASCADE).
`owner_id`는 RESTRICT라 승계·해산 없이 user를 지우면 실패하게 둠.

> **범위 주의**: 하드 삭제 배치와 그룹 승계/해산은 **현재 Kotlin에 없는 신규 기능**입니다
> (승계는 Flask `_handleGroupOwner`에만 있었음). 스키마는 이 결정을 담되,
> 구현은 [작업중.md](작업중.md) 본 순서와 **별도 범위**로 둡니다.

> **`chk_groups_counter` 부작용 하나**: 운영자가 `member_max_count`를 현재 인원보다
> 낮추면 UPDATE가 실패합니다. 정원 축소 시 인원을 먼저 줄여야 한다는 뜻 —
> 의도한 동작이지만 알고 있어야 합니다.

### 4-2. 인덱스와 그 근거

| 인덱스 | 어떤 쿼리를 위한 것인가 |
|--------|----------------------|
| `uk_commits_user_sha (user_id, sha)` | C1 벌크 업서트·중복 skip |
| `idx_commits_user_date (user_id, commit_date)` | C2 최근 7일, C3 두 달 잔디, **C4 난이도별**, G2 멤버별 월 집계, R2 폴백 |
| `idx_commits_date_user (commit_date, user_id)` | R3 이번 달 전체 `GROUP BY user_id` — 월 구간 스캔 후 user만으로 커버 |
| `uk_groups_name` / `group_name` UNIQUE | G5 중복 확인, G6 `LIKE 'abc%'` 앞부분 검색 |
| `idx_participate_user (user_id)` | G1 유저가 속한 그룹 목록 (`uk (group_id,user_id)`만으로는 user→groups 역방향이 비효율) |
| `idx_participate_group_created (group_id, created_at)` | 탈퇴 시 승계용 최연장자, G2 멤버 목록 |
| `idx_users_deactivated (deactivated_at)` | 7일 하드 삭제 배치 |
| `idx_history_user_problem (user_id, problem_num, solve_time)` | H1 문제당 PB — `MIN(solve_time)`을 인덱스만으로 |
| `idx_history_user_solved (user_id, solved_at)` | H1 최근 풀이 목록 |

**뺀 인덱스**

- ~~`idx_commits_user_level (user_id, level)`~~ — `commits`는 연 1억 건에 벌크 삽입이 주 경로라
  인덱스 하나가 곧 쓰기 비용입니다. C4는 프로필 화면이라 빈도가 낮고
  `idx_commits_user_date`로 user_id를 좁히면 커버됩니다. **측정 후 필요하면 추가.**
  현재 `commits` 인덱스는 PK 포함 4개.

> `history`는 쓰기가 적어 인덱스 2개를 둡니다. `commits`와 계산이 다릅니다 —
> 인덱스 개수 기준을 테이블 성격 무시하고 일률 적용하지 않습니다.

### 4-3. 3장 결정사항에 대한 내 답

| # | 무엇을 골랐나 | 왜 |
|---|--------------|-----|
| 1 | **다중 그룹 참여 허용**(요구사항). 스키마는 M:N(`participate`), `(group_id,user_id)` UNIQUE로 중복 참여만 막음. 유저당 상한 ≤5는 **앱에서 처리, 트리거 안 씀** | 상한은 데이터 무결성이 아니라 남용 방지라 DB 불변식이 아님. 트리거는 테스트·디버깅 비용이 이득보다 큼. **현재 앱의 `participations.first()`가 요구사항 위반 → 앱 버그로 등록** |
| 2 | 커밋 유일성 = **`UNIQUE(user_id, sha)`**. 대리키 `commit_id`는 PK로 **유지**. sha = Git 커밋 ID | 포크 시 sha 전역 충돌 방지. `commit_id`는 업서트 키가 아니라 조회/대시보드용 대리키 |
| 3 | 탈퇴: **소프트 삭제 7일**(`deactivated_at` 단일 컬럼, 랭킹·그룹·집계 **제외**) → 배치 **하드 삭제**. 닉·`github_id` **재사용 허용**(하드 삭제 후). 그룹: 마지막 멤버면 해산, 아니면 **잔여 최연장자 승계**. Spring `owner` `updatable=false` 수정 필요 | 쿨다운 후 식별자 슬롯 반환. 소유권은 Flask 승계를 따름. **`active` 제거** — `deactivated_at IS NULL`이 곧 활성이라 두 컬럼은 같은 사실의 중복이었음 |
| 4 | history: **`solve_time` INT**(소요 시간, 초 단위 권장) + **`solved_at` DATETIME**(푼 시각, 워치 확장). 문자열 `"HH:MM:SS"` 폐기 | 합산·정렬·최근 풀이에 타입이 맞아야 함 |
| 5 | history는 **append-only**. 모든 풀이를 남기고 문제당 최단(PB)은 `MIN(solve_time)`으로 조회. **랭킹은 이번 달 커밋 수**. 같은 문제·다른 날 커밋도 sha가 다르면 **각각 카운트**. 커밋에 problem_num은 필수 아님 | PB(history)와 독촉 랭킹(commits) 역할 분리. `UNIQUE(user_id, problem_num)`로 최단만 남기면 **이력이 사라져 테이블 이름과 내용이 어긋남** — 상태 컬럼만 두고 과거를 잃는 전형 |
| 6 | `level` = **VARCHAR**, 세부 티어(`GOLD IV`) + `UNRATED` 허용. DB ENUM/CHECK 없음(**A**). 백준허브(·타 플랫폼) 메시지를 신뢰·반영 | solved.ac 밖·타 플랫폼은 난이도 없을 수 있음. 이상한 문자열 위험은 감수(의도적) |
| 7 | 정원 불변식을 **DB가 선언**한다: `CHECK(0 <= member_counter <= member_max_count)` + `CHECK(member_max_count >= 1)`. 증가는 원자적 조건부 UPDATE | 앱만 막으면 한 줄 버그에 데이터가 깨짐(기존 leave 카운터 드리프트 선례). **락+COUNT 방식은 정확하긴 하나 방어선이 전부 앱으로 옮겨간다** — 앱을 못 믿어서 컬럼을 뺐는데 뺀 결과 앱만 남는 역전 |
| 8 | **`member_counter` 유지** | 이 프로젝트에서 이 컬럼은 성능 최적화가 아니라 **원자적 조건부 갱신을 가능하게 하는 장치**. 드리프트의 원인은 역정규화가 아니라 `leaveGroup`의 무조건 감소라는 **버그 한 줄**이었으므로, 컬럼 제거는 과교정. 버그를 고치고 CHECK로 봉인 |

### 4-4. 의도적으로 하지 않은 것

> "몰라서 안 한 것"과 "판단해서 뺀 것"은 완전히 다르게 읽힙니다. 여기에 적으세요.

- **`member_counter` 제거** — **검토 후 되돌림.** 정규화 기본값으로는 제거가 맞지만,
  이 컬럼은 성능 최적화가 아니라 원자적 조건부 갱신 장치이고
  드리프트 원인은 역정규화가 아니라 버그 한 줄이었음 (위 8)
- **유저당 그룹 상한을 DB로 강제** — 안 함. "행 수 ≤ N"은 선언형으로 불가하고,
  트리거는 테스트·디버깅 비용이 이득보다 큼. 이건 무결성이 아니라 남용 방지라 앱 소관 (위 1)
- **level ENUM/CHECK** — 판단해서 안 함 (백준허브 신뢰). **다만 근거가 약한 것을 인지함** —
  이미 알 수 없는 값이 들어와 `UNRATED` fallback을 넣은 이력이 있음(`55a4861`)
- **커밋에 `problem_num`** — 랭킹이 커밋 수라 필수 아님. 넣지 않음(필요해지면 파싱 추가)
- **그룹장 제거** — 검토 후 안 함. Flask 승계 유지
- **소프트 삭제 보관 = 7일** (재가입 쿨다운과 동일). 하드 삭제 전까지 닉·github UNIQUE 점유
- **`commit_url` 정규화** — 안 함. `sha`+`github_id`+`repo`로 유도 가능한 중복이지만,
  GitHub URL 형식 변경에 대한 방어이기도 함. 우선순위 낮음
- **Flyway** — 안 함. 스키마 변경이 이번 범위에 없고, Flyway도 DDL은 손으로 씀 → [작업중.md](작업중.md) 0단계

## 5. 대조 기준 — 다 짜시면 이걸로 봅니다

미리 공개합니다. 짜면서 스스로 점검하셔도 됩니다.

1. **2장의 모든 쿼리가 인덱스를 타는가.** 특히 R3(전체 유저 월별 집계)와
   G2(멤버 여러 명의 두 달치 집계)가 테이블 접근 없이 인덱스만으로 끝나는가
2. **불변식이 DB에 선언되어 있는가.** 애플리케이션 코드가 유일한 방어선인 규칙이 남아 있는가
3. **스키마가 허용하는 범위 = 애플리케이션이 가정하는 범위인가.** 어긋나면 조용한 버그가 됩니다
4. **타입이 의미에 맞는가.** 정렬·집계해야 하는 값이 문자열로 들어가 있지 않은가
5. **소프트 삭제와 UNIQUE·FK의 상호작용을 처리했는가**
6. **역정규화가 있다면 근거와 갱신 방법이 명시되어 있는가**
7. **엔티티 클래스와 DDL 중 무엇이 진실인지 정해져 있는가.**
   지금은 정해져 있지 않아서 두 군데가 이미 어긋나 있습니다
