## 2단계 — 버그 A (핵심)

### 무슨 일이 일어나고 있나

커밋을 가져올 때 서버가 이 순서로 일합니다.

1. 깃허브에서 커밋 **5개**를 받아온다
2. DB에 저장한다 — **이미 있는 건 안 넣는다**
3. 랭킹 점수를 올린다 — **그런데 그냥 "5점"을 더한다**

2번과 3번이 따로 놉니다. 2번에서 실제로 **0개**만 들어갔어도 3번은 5점을 더합니다.
버튼을 세 번 누르면 DB는 커밋 5개 그대로인데 랭킹은 **15점**이 됩니다.

### 스케줄러가 왜 안 고쳐주나

매시간 도는 스케줄러는 "DB를 세어보고 랭킹 점수를 맞추는" 일을 하는데,
**점수를 올리기만 하고 내리지는 않게** 되어 있습니다.

그렇게 만든 이유가 있습니다. 스케줄러가 DB를 세는 동안 사용자가 새 커밋을 올리면,
스케줄러가 방금 오른 점수를 옛날 숫자로 덮어써서 없애버립니다.
그걸 막으려고 **"지금 점수보다 클 때만 바꾼다"** 는 규칙을 넣었습니다.

```
랭킹 점수: 15점
DB 실제:    5개

스케줄러: "5는 15보다 작네. 안 바꿔."
→ 15점 그대로. 영원히.
```

**안전장치 두 개가 서로를 막고 있습니다.** 하나는 점수를 부풀리고, 다른 하나는 그걸 못 내리게 합니다.

### 왜 지금까지 몰랐나

부하 테스트용 가짜 깃허브가 **매번 새 커밋을 만들어냈습니다.**
중복이 생길 수가 없으니 이 버그가 나타날 방법이 없었습니다.

### 고치는 법

3번에서 "5개"가 아니라 **"실제로 들어간 개수"** 를 더합니다.
그러면 점수가 애초에 안 부풀어서 스케줄러가 내릴 일도 없어집니다.
**규칙("올리기만 한다")은 그대로 둡니다.** 그게 틀린 게 아니라 틀린 숫자를 넣은 게 문제였으니까요.

> 면접에서 강한 이유: "버그를 찾았다"가 아니라
> **"내가 넣은 안전장치 두 개가 서로를 방해하는 걸 발견했다"** 이기 때문입니다.
> 하나는 남이 봐도 찾지만, 둘의 상호작용은 자기 설계를 이해해야 보입니다.

- [x] `RankService.kt` — `private fun`에 `@Transactional`. self-invocation이라
      AOP 프록시가 못 잡아 애초에 무효. 제거 (JpaRepository가 자체 트랜잭션 보유)
- [x] `GroupService.createGroup` — `joinGroup`과 순서 통일(증가 먼저, 확인 후 참여 기록).
      `maxCount=0` 같은 값을 `GroupFullException`으로 막음
- [x] **`createGroup` 응답의 `memberCount`가 항상 0으로 나감** — 원래 코드의 실제 API 버그.
      `incrementMemberCounterIfNotFull()`은 벌크 UPDATE라 DB만 바꾸고 Hibernate 세터를
      안 거치므로, `return group`이 증가 전 값(0)을 그대로 내보냈다.
      그룹을 만들면 본인이 자동 멤버가 되는데도 응답은 "멤버 0명"이었음.
      "잠복"이라고 적어뒀던 게 사실은 눈에 보이는 버그였다.
      - 빨간불 확인: `expected: 1 but was: 0`
      - 증명 테스트: **`GroupCreateResponseTest`**
      - 수정: 증가 후 `findById`로 재조회해서 반환.
        이때 1차 캐시가 아니라 DB를 읽게 하려고 `@Modifying`에
        `clearAutomatically = true`가 필요했음

> **아래는 원래 코드의 결함이 아니라, 위 수정 중 이 세션에서 새로 만든 회귀입니다.**
>
> 원래 `@Modifying`에는 아무 옵션도 없었고 정상 동작했다.
> `clearAutomatically`를 넣으면서 `flushAutomatically`를 빠뜨렸더니,
> 아직 DB에 안 쓰인 `deleteByGroupAndUser`의 삭제가 `clear()`에 통째로 버려져
> `GroupLeaveTest`가 깨졌다 (`[45L, 46L]` — 지워졌어야 할 참가자가 남음).
> 두 벌크 UPDATE는 `groups` 테이블만 건드려서 `participate`의 대기 삭제와
> query space가 겹치지 않아 Hibernate 자동 flush도 일어나지 않았다.
> `flushAutomatically = true`를 같이 넣어 해결.
>
> **레거시 결함 목록에 넣지 말 것.** 테스트가 있어서 즉시 걸린 사례일 뿐이다
> — 오히려 3단계에서 쌓은 테스트가 값을 한 증거로 쓰는 게 맞다.
